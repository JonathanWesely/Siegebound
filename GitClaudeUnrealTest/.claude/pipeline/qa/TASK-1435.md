## ⚖️ RULING 1 — THE NON-REGISTRATION IS **UPHELD**. Refusing leaves **NO** human-reachable action on this screen agent-unreachable.

**The ruling, stated as a ruling:** `USiegeAssistantConsoleWidget` may ship **without** calling `RegisterMenuNavTarget`, and the refusal is **correct**, not a scope dodge. I verified the load-bearing premise at source rather than accepting it, and I tested it against 🧑 Jonathan's standing instruction — *"the agent should be able to do everything a human can do"* — not against the row's convenience.

**(a) VERIFIED AT SOURCE: the tree builds no button.** `ConstructConsoleTree` makes exactly **seven** `WidgetTree->ConstructWidget<>` calls — `RootPanel` (`UVerticalBox`), `ConsoleTopSpacer` (`USpacer`), `ConsoleBackdrop` (`UBorder`), `ConsoleColumn` (`UVerticalBox`), `TranscriptText` + `StatusText` (`UTextBlock`), `InputBox` (`UEditableTextBox`). **No `UButton` is constructed anywhere in the file** — the only `UButton` token in the `.cpp` is a comment, and `ConfirmButton` is a `BindWidgetOptional` `TObjectPtr` that is null on the v1 code-authored path (its own construction log prints `ConfirmButton bound from an asset tree=%d`). `IsNavFocusStop` admits `UEditableTextBox` unconditionally (`SiegeMenuInputSubsystem.cpp`, the `IsA<UEditableTextBox>()` branch, *"a text box is keyboard-focusable by construction"*). ⇒ **one stop, and it is the text box.** The row's (a) stands as measured. **The dispatch's fail condition — "if a button exists anywhere in that tree, the refusal is wrong" — is NOT met.**

**THE PARITY TEST, ANSWERED IN ITS OWN TERMS.** The human actions available on this screen, and what the agent holds for each:

| # | what a human can do here | mechanism | agent's reach today |
|---|---|---|---|
| H1 | type characters into the box | Slate char events on the focused box | `AppendToInput(FString)` — `BlueprintCallable`, and it is already the war map's shipped channel for putting text in this box |
| H2 | `Enter` → submit | Slate `HandleCarriageReturn` | `SubmitPressed(FString)` — `BlueprintCallable` |
| H3 | `Enter` on an empty box → close (route 4) | Slate → `HandleTextCommitted` | outcome via `CloseConsole()` — `BlueprintCallable` (the thunk itself is a bare `UFUNCTION()`, so the *route* is not reflection-callable — ⛔ and registration would not change that) |
| H4 | positional `Z` → accept a confirm prompt | `NativeOnPreviewKeyDown` tunnel | `ConfirmPressed()` — `BlueprintCallable`; **and now `MenuAcceptPressed()`, this diff's new one** |
| H5 | the open key → toggle open/close | `IA_AssistantConsole` (Enhanced Input) | injectable as an action **and** `ToggleConsole()`/`OpenConsole()` — reachable twice over |
| H6 | click into the box to focus it | Slate pointer | focus is asserted **unconditionally on every open path** (`:513`, `:620`) and re-asserted after submit (`:697`, `:714`) — the state needs no agent act |

**⇒ ANSWER: NO. Nothing a human can do on this screen becomes unreachable by refusing.** The single capability registration would add is *"move focus onto the one stop"* — i.e. re-focus a box the widget already focuses on every open path and re-asserts after every submit. That is not an action; it is a recovery from having left the screen, and the agent reaches it anyway through `OpenConsole()` / `AppendToInput()`, both of which call `FocusInputBox()`.

**⭐ AND THE ANSWER IS INVARIANT TO THE ONE THING I COULD NOT VERIFY.** If the verification lane holds *only* `UEnhancedInputLocalPlayerSubsystem::InjectInputForAction` and no reflection route, then H1–H4 are out of its reach — **but they are equally out of reach WITH registration**, because registration delivers only the four nav verbs and every one of them is a no-op or a decline on this tree: `MoveFocus(±1)` computes `WrapIndex(0, ±1, 1) = 0` and re-focuses the box it is on; `HandleMenuAccept` fails both `Cast<UCheckBox>` and `Cast<UButton>` on a `UEditableTextBox` and takes the declined branch (*"has no Accept semantics (or nothing is focused)"*); `StepFocusedStop` declines for the same reason; `IA_MenuBack` is inert (see Ruling 2). ⇒ **registration buys the agent exactly zero actions under either assumption about its lane.** The conclusion does not depend on a capability I did not measure, and that is why I am willing to state it as a ruling.

**(d) IS THE STRONGEST LIMB AND I CONFIRM IT AT THE INSTALLED ENGINE SOURCE.** `FSlateEditableTextLayout::HandleKeyDown` routes `EKeys::Up` and `EKeys::Down` through `BoolToReply(MoveCursor(...))` (the two vertical branches), and `MoveCursor`'s non-multiline path carries the engine's own comment verbatim — *"Vertical movement not supported on single-line editable text controls - return false so we fallback to generic widget navigation"* — followed by `return false;`. ⇒ `Up`/`Down` are **Unhandled by the box, bubble past it, and reach Enhanced Input while the box has focus.** With focus *outside* the box — a normal in-match state, because §2 makes the root `SelfHitTestInvisible` precisely so the player can keep clicking the battlefield through the panel — `Up` would drive `MoveFocus(-1)` → `FocusWidget(InputBox)` and **yank keyboard focus into a chat box in the middle of a fight, on a key that does nothing in this game today.** That is the same defect class as `TASK-1429`'s *"a match where the arrow keys belong to a menu"*, and it is a regression this row would have *introduced* had it registered. Declining is the correct call.

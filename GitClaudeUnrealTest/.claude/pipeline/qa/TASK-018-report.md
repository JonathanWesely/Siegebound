## Ruling on the two questions the programmer asked

- **Broadcast ordering in TakeDamage (HP broadcast BEFORE HandleDestroyed)**: CORRECT and preferred. Events fire in the order state changes occur: listeners receive the (0, 2000) value while the bar still exists, then the destroyed event hides it. Reversing the order would hide the bar before it could ever render 0 and would let HP-listeners observe a hidden castle at a nonzero last-known value. The TASK-002 contract (destroyed broadcast fires after hide/collision-off) is preserved inside `HandleDestroyed`.
- **Every-broadcast-is-a-real-change proof**: ACCEPTED, with its boundary documented as WARN-1 — the proof assumes no listener mutates the castle re-entrantly from inside the broadcast. True for every M1 listener (the bar is view-only).

## Findings

1. **[warning — theoretical, no change required]** `Castle.cpp:157-162` — between the (0, MaxHP) broadcast and `HandleDestroyed()`, `bDestroyed` is still false. A listener that synchronously damages this castle from inside its `OnCastleHPChanged` handler would re-enter `TakeDamage` with `CurrentHP == 0`, producing one duplicate no-change (0, MaxHP) broadcast, and `IsCastleDestroyed()` briefly reads false at 0 HP during the broadcast. `FOnCastleDestroyed` still fires exactly once regardless (the `bDestroyed` guard holds). No M1 listener can trigger this (the bar never mutates the castle). **Carry-forward for M2+**: anything that binds `OnCastleHPChanged` and mutates castle state must not do so synchronously in the handler, or an equality/`bDestroyed` re-check must be added at the broadcast site.
2. **[nit — handoff accuracy only, not code]** Flagged decision 2's rationale says a manual second `InitWidget()` call "would recreate the widget" — in fact `InitWidget` self-guards on an existing widget instance. The omission of the defensive call is still the right call; noting so the record is accurate if anyone revisits this.
3. **[nit]** `Castle.h:84` — `GetCurrentHP` doc comment still reads "HUD/QA hook (TASK-011)"; it is now also the seed source for TASK-018/019. Cosmetic.
4. **[nit — pre-existing pattern]** `Castle.h:157` — `CurrentHP = 2000.0f` default duplicates `MaxHP`'s default as a literal (same pattern as TASK-005 minor 3); harmless since BeginPlay reseeds from `MaxHP` before anything reads it.

## Flagged-decision rulings (all 9)

1. **Explicit `SetVisibility` on HPBarWidget instead of relying on `SetActorHiddenInGame` — PASS (required, not optional).** Confirmed: the screen-space viewport layer is gated on the COMPONENT's `IsVisible()` in `UWidgetComponent`'s tick; `SetActorHiddenInGame` sets actor `bHidden`, which primitive scene rendering respects but the screen layer does not consult. Without the explicit call the bar would keep floating over a destroyed castle. Programmer read the engine correctly.
2. **Rely on post-BeginPlay `SetWidgetClass` → `InitWidget()` — PASS.** The engine calls `InitWidget()` from `SetWidgetClass` when the component has begun play, Slate is initialized, and the class changed — and here the class always changes (constructor default is null, `SetWidgetClass` is only reached with a non-null loaded class). No defensive `InitWidget()` needed (and see nit 2: it would be safe anyway, just redundant). Editor/commandlet worlds never reach this path (no BeginPlay / Slate gate) — silent no-op, acceptable.
3. **Plain `UCLASS()`, not `UCLASS(Abstract)` — ACCEPTED.** Correct risk call: TASK-019's MCP reparent flow is unproven against Abstract parents, a non-abstract base costs nothing, and nothing ever spawns the C++ base directly. Do not change to Abstract before TASK-019 lands.
4. **Explicit forwarding `UFUNCTION` handler instead of AddDynamic on the BIE — PASS.** Binding the BIE directly would work (name-based ProcessEvent), but the explicit handler makes the `RemoveDynamic` in the re-target path unambiguous and keeps the BIE a pure view hook. No behavior difference; better maintainability.
5. **Re-target support in InitForCastle beyond the spec letter — ACCEPTED, not scope creep.** ~6 lines, correct (removes the old castle's binding before adopting the new one, so a bar can never receive two update streams; `AddUniqueDynamic` makes same-castle repeats a pure re-seed). Cheap insurance for PlayAgain-era widget churn; failing this would buy nothing.
6. **No log when WBP_CastleHealthBar is missing — ACCEPTED.** The spec's explicit "silent no-op, never a crash" wording wins over the log-once house style. Risk is contained: TASK-019's PIE acceptance (bar visible at boot) will immediately surface a bad path or class. No Verbose log required.
7. **Explicit `SetCollisionEnabled(NoCollision)` on HPBarWidget — ACCEPTED.** Beyond spec but consistent with the QA-pre-approved TASK-002 precedent of not resting gameplay contracts (TASK-007 cursor trace, TASK-004 acquisition) on implicit engine defaults. Harmless for a screen-space component.
8. **No NativeDestruct unbind — ACCEPTED.** Dynamic multicast delegates hold weak object references and skip/compact dead listeners — no dangling-callback risk. Lifetimes are coupled anyway (castle owns component owns widget). Deliberate omission is sound.
9. **BeginPlay seed broadcast fires before the widget exists — PASS.** The bar does not consume that broadcast; `InitForCastle` seeds it directly from the getters (seed-then-bind), and the BeginPlay broadcast serves pre-bound listeners per spec. Both orderings are correct for the bar; concur with the handoff's note — do NOT "fix" this into a double-seed.

## Findings

- [WARN] SiegeSessionSubsystem.cpp:274/293/316 — **Post-travel error visibility gap.** Every mid-session failure broadcasts its error FString *before or during* the return-to-menu travel — i.e. while no `USessionMenuWidget` is alive to hear it (the widget lives only in the menu world). The freshly constructed menu widget starts blank, so on a mid-match disconnect the user lands on the menu with no visible reason (log-only). Compounding it: in the client-failure path, `OnSessionError` fires and then `LeaveMatch()`'s `OnSessionStatus` ("Returning to the main menu...") fires — and `HandleSessionStatus` (SessionMenuWidget.cpp:153-159) deliberately clears the error line, so even a live widget would wipe the error instantly on that path. The doc-§5 NAMED case — bad IP — is fully correct (menu world persists standalone, widget alive, error shows, no travel, no hang: gate (f) holds), so this is not gate-blocking. Suggested (P1-acceptable to defer): cache `LastSessionError` in the subsystem and have the widget pull it at `NativeConstruct`; and/or broadcast the leave-status before the error-broadcast order matters. Record in TASK-357's checklist either way.
- [WARN] SiegeSessionSubsystem.cpp:302 — **Host-side "Opponent disconnected." is log-only in P1** (tied to flagged decision 3, which I pass — see rulings). The status broadcast has no in-arena listener; the host learns of the joiner drop only via `LogSiegeNet`. Acceptable for the P1 state-visibility gate; TASK-357 must verify the LOG observable, not a UI one, and the P2 in-match surface should pick this up.
- [NIT] SiegeSessionSubsystem.cpp:236 — Leading-zero octets are accepted (`010.0.0.1`, `192.168.001.050`). Some resolvers treat leading-zero octets as octal or reject them; either way the join degrades gracefully through the existing timeout→error path (no hang), but rejecting `Len > 1 && starts-with-'0'` octets would be strictly cleaner.
- [NIT] SiegeSessionSubsystem.cpp:69-87 — `HostListenMatch()` has no in-flight latch (unlike Join/Leave): a double-press dispatches two travels to the same destination. Benign (second travel supersedes the first, same URL), just asymmetric with the rest of the class.

The code documents exactly this and dynamic delegates handle it safely; noted for completeness only.

## 🚨 THE RULING YOU ASKED FOR — `RegisterSelfDrivingMenuNavTarget` vs `RegisterMenuNavTarget`

### **OVERRULED. Use the plain `RegisterMenuNavTarget`. One identifier. This is BLOCKER-1.**

The handoff's §4 argument has two premises. **I measured both, and both fail.**

**Premise A — "three of the four suppressed behaviours are structurally unreachable here, so declining them subtracts nothing that could ever have run."**
❌ **False for the only input verb an agent holds.** `MoveFocus`, `HandleMenuAccept` and `StepFocusedStop` are unreachable *by a real key*; they are fully reachable by `InjectInputForAction`, which is **the** agent door in this project — `SiegeMenuInputSubsystem.h:164-165` (*"What DOES reach them: `UEnhancedInputLocalPlayerSubsystem::InjectInputForAction` (Aura's `inject_input_action`, and the automation test) — that is the door the row names"*) and `:170` (*"no real-input lane exists for an agent"*), with the live call at `Tests/SiegeMenuInputTest.cpp:166`. So with the flag set, an injected `IA_MenuAccept` reaches `HandleMenuAccept`'s **first statement** — `DeclineIfActiveTargetSelfDriving(TEXT("IA_MenuAccept"))` (`:1558`) — and returns. **The agent cannot press Play Again.**
Without the flag it works end to end, verified statement by statement: `HandleMenuAccept` → `IsNavTargetActionable()` (true, because registered) → `GetFocusedNavStop()` returns `Btn_Jump` (it is focused by `SetWidgetToFocus`, and `HasUserFocus` does not care about the focus *cause*) → `Focused->OnClicked.Broadcast()` → the graph's `OnClicked_Event` → `RequestPlayAgain`.

**Premise B — "`FocusFirstNavStop()` would race the shipped `SetWidgetToFocus`, and the ordering is unmeasured."**
❌ **The ordering is determinate, and it converges.** I measured it:
- **(a) Stop 0 IS the by-name target.** Live widget tree (`get_asset_meta`): `Overlay_19 → SizeBox_0 → Button "Btn_Jump"`, plus `UI_Thumbstick_C "Thumbstick_Move"` and `"Thumbstick_Aim"`, **both `Visibility=Collapsed`** and both Blueprint `UUserWidget`s. Admitted-class population = **exactly one `UButton`**. So `Stops[0] == Btn_Jump` **by construction**, not by luck.
- **(b) The order of operations is fixed by the call site.** The registration is placed *after* `SetInputMode(InputMode)`. `SetInputMode` only **defers** its focus request into `LocalPlayer->GetSlateOperations()`. `FocusFirstNavStop()` → `FocusWidget()` then does an **immediate** `FSlateApplication::SetUserFocus(..., EFocusCause::Navigation)`; on success it calls `DelayedSlateOperations.CancelFocusRequest()`, and `FReply::CancelFocusRequest` (`Reply.cpp:60-67`) clears **only** `bSetUserFocus` / `FocusRecipient` / `bReleaseUserFocus` — the input mode's mouse-capture and lock operations survive untouched. On failure it writes `SetUserFocus(..., Navigation)` into the **same** `FReply`, replacing the deferred `SetDirectly` request. **Either branch ends with the same widget focused, with cause `Navigation`.**
- **(c) The degenerate branch is safe.** If the walk returned zero stops, `FocusFirstNavStop` returns false *without* cancelling anything and today's `SetWidgetToFocus` behaviour survives verbatim.
⇒ **There is no branch in which the plain call is worse than the shipped one.**

**And the cost the handoff never stated — the flag forfeits the focus ring, which is the first half of this row's own 🧑 sitting sentence.**
`FInputModeDataBase::SetFocusAndLocking` uses `SlateOperations.SetUserFocus(Widget)` with the **default cause `EFocusCause::SetDirectly`** (`PlayerController.cpp:6317`). `FSlateApplication` computes `ShowFocus = (InCause == EFocusCause::Navigation)` (`SlateApplication.cpp:3096-3099`), and the one path-override that applies in a game viewport — `UGameViewportClient::QueryShowFocus` (`GameViewportClient.cpp:2618-2630`) — returns **false** for a non-`Navigation` cause under `ERenderFocusRule::NavigationOnly`, which is the **engine default** (`UserInterfaceSettings.cpp:16`) and is **not overridden anywhere in this project's `Config/`**. `SWidget::Paint` draws `GetFocusBrush()` only when `ShowUserFocus` is true (`SWidget.cpp:1744-1751`).
⇒ **Under the shipped self-driving registration, `Btn_Jump` can never wear the dashed focus rectangle.** The subsystem's own header says the visible focus state of this whole epic exists *because* `FocusWidget` uses `EFocusCause::Navigation` (`SiegeMenuInputSubsystem.h:173-183`). The victory screen would be **the one screen of the ten with no ring**, and `cl. 3(b)`'s first clause is *"is there an outline on the Play Again button"*.

**The fix:** `RegisterSelfDrivingMenuNavTarget(VictoryWidget)` → `RegisterMenuNavTarget(VictoryWidget)`, one line, one site, plus the surrounding comment paragraph re-argued (it currently teaches the false premise). Nothing else in the row changes.

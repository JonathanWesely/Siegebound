### BLOCKER A (TASK-156) — `DamageNumberActor.cpp:78-79` — MOST VEXING PARSE
### BLOCKER B (TASK-159) — `SummonedUnit.cpp:236-237` — MOST VEXING PARSE (same class)
ROOT CAUSE (byte-verified; NOT a missing include). Both `.cpp` include their headers which both carry
`#include "UObject/SoftObjectPtr.h"` (`DamageNumberActor.h:7`, `SummonedUnit.h:7`), so `TSoftClassPtr`/
`TSoftObjectPtr` (and their `LoadSynchronous()` members) are COMPLETE types in both TUs. The declared
types are correct and DO have `LoadSynchronous()`. The failure is a C++ **most-vexing-parse**:

- `DamageNumberActor.cpp:78`: `const TSoftClassPtr<UUserWidget> WidgetClass(FSoftObjectPath(DamageNumberWidgetClassPath));`
- `SummonedUnit.cpp:236`:     `const TSoftObjectPtr<USkeletalMesh> SkSoft(FSoftObjectPath(SkPath));`

In each, the inner `FSoftObjectPath(Ident)` is grammatically ambiguous: redundant parentheses around a
parameter name are legal, so `FSoftObjectPath(DamageNumberWidgetClassPath)` parses as a parameter
declaration `FSoftObjectPath DamageNumberWidgetClassPath` (the fact that an identically-named *variable*
is in scope does NOT disambiguate — the standard's "if it can be a declaration, it is" rule wins). The
whole statement is therefore parsed as a **function declaration** — `WidgetClass`/`SkSoft` become
FUNCTIONS returning the soft-ptr type, not objects. On the next line `WidgetClass.LoadSynchronous()` /

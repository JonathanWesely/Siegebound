## 3. 🚨 THE AUTHOR'S OWN FLAGGED QUESTION — `ResetFog` DESTROYING INSIDE `PlayAgain`'s `TActorIterator`

**RULING: THE CODE IS SAFE. THE CONCLUSION HOLDS. THE STATED GROUND IS NOT THE ONE THAT MAKES IT
HOLD IN UE 5.8 — and I settled it by reading the engine, not by arguing.**

The author's ground (`FogVolume.cpp:265-268`): *"UWorld's removal NULLS the level's actor slot
rather than compacting the array, so no index the iterator still holds can shift."*
That sentence is **factually true** — `UWorld::RemoveActor`, `Engine/Private/World.cpp:2892`:
`CheckLevel->Actors[ActorListIndex] = nullptr;` — **but it is about a data structure
`TActorIterator` does not read in 5.8.**

**The operative mechanism, read from `Engine/Public/EngineUtils.h` (UE_5.8):**
- `FActorIteratorState` (`:151-167`) holds its **own private snapshot** `TArray<AActor*> ActorArray`,
  built once in the constructor from `GetObjectsOfClass` / the world's pre-filtered actor list. It
  **never** indexes `ULevel::Actors`.
- `TActorIteratorBase::operator++` (`:324-334`) caches `const int32 LocalActorArrayNum =
  LocalActorArray.Num();` under the engine's own comment *"LocalActorArray is immutable within the
  loop"*.
⇒ **Destroying an unrelated actor mid-iteration cannot shift, reallocate or invalidate anything the
iterator holds.** The conclusion is right for a stronger reason than the one given.

**Two further engine facts that close it in the other direction too — neither is in the handoff:**
1. `EActorIteratorFlags::SkipPendingKill` is **on by default** and `IsActorSuitable` (`:441-446`)
   re-tests `IsValid(Actor)` at every `++`. So even destroying an actor that **is** in the snapshot
   only causes it to be **skipped**, never dereferenced dangling.
2. The iterator **appends actors spawned during iteration** (`SpawnedActorArray`, fed by an
   `OnActorSpawned` delegate) and `TActorIterator::operator*` is a **`CastChecked<ActorType>`** —
   i.e. a *spawn* of the wrong class during the loop would be the dangerous direction. It is closed
   **twice**: the handler filters with `if (InActor->IsA(DesiredClass))` (`:285`) and `BP_SiegeFog`
   is a `BP_FogArea_C` child, **not** an `AFogVolume`; and on the reset path `RefreshFogVisual`
   cannot take the spawn branch at all, because `ResetFog` just zeroed the deadline so
   `IsFogActive()` is false.

⇒ **No crash on match restart. This does NOT need execution to settle** — it is settled by the
engine source. See NIT-1 for the comment repair this implies (a future reader who trusts the stated

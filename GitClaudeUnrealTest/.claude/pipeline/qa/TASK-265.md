## 🚩 RULING ON THE FLAGGED DEVIATION — **ACCEPTED. Ship as written. Reconcile the board + CONVENTIONS to the code.**

**What shipped vs. what the board said.** The board/CONVENTIONS say: pass through an already-eligible anchor, *else per-axis clamp about `GetCastleRedLocation()`* (castle box only). The programmer shipped: pass-through unchanged, else clamp to **the nearer of the two eligible regions** — castle box, or a Red-owned `CaptureZone_Center` (`SiegeBotController.cpp:1122–1174`, isolated in a `--- FLAGGED DEVIATION ---` comment block).

**I verified each of the programmer's four claims independently.**

1. **Inert with no zone / Neutral zone / Blue-owned zone — TRUE, verified.**
   - No zone placed: `TActorIterator<ACaptureZone>` yields nothing, `MidZone == nullptr`, the whole block is skipped → `BoxClamped` returned (`:1141–1153`).
   - Neutral / Blue-owned: the branch is gated on `MidZone->CanTeamSpawnHere(ETeamId::Red, ZoneClamped)`, which is `IsPointInZone(Point) && CaptureOwner == TeamToState(Team)` (`CaptureZone.cpp:120–125`). Neutral matches no team; Blue-owned fails the Red query → `BoxClamped` returned.
   - In all three cases the result is byte-identical to the board's literal clamp. **Claim confirmed.**

2. **Castle-relative anchors are always nearer the box (ruling #1 / attack waves untouched) — TRUE at the shipped geometry, verified by arithmetic.**
   Rule-1 unit and rule-4 attack anchor at `CastleRed + (−1750, ±900, 0)` ⇒ (23 250, |Y| ≤ 900). `BoxClamped` = (24 200, ≤ ±800) ⇒ distance ≈ 950 uu. `ZoneClamped` = (800, …) ⇒ distance ≈ 22 450 uu. Box wins by ~23×; the strict `<` in the comparison (`:1168`) also breaks ties toward the box. The box only loses for anchors with X ≲ 12 500 (the midpoint between the two clamp targets), i.e. only the far-flung rule-2 economy anchors. Generalized: the zone could only win for a castle-front anchor if `Castle_Red.X < ~3 500`, a degenerate layout where the castle box and the mid zone would overlap anyway. **Claim confirmed. M7.6 ruling #1 and rule-4 wave behavior are untouched; the bot gets no free forward spawn for its army.**

3. **It preserves TASK-264 PIE result (f) — TRUE, and this is the decisive point.**
   The board records (f) verbatim: "*the bot demonstrably staged 2 units mid-field only while Red held the zone*". I traced the mechanism: rule-2a's anchor is `Mine + 400 toward castle`, then `if (!IsOnOwnHalf(Desired.X)) Desired.X = BotHalfBoundaryX;` (`:555–558`) — a Blue-half mine parks the anchor at X = 0, and the 1 100-uu ring reaches into the ±840 zone, which `IsBotHalfPointClear` accepts while Red owns it. That is exactly (f). A castle-box-only clamp moves those anchors to X ≈ 24 200 and the ring (max 1 100) can then never reach mid ⇒ **(f) is deleted and TASK-266 acceptance (e) fails by construction.** The deviation preserves it and makes it deterministic rather than luck-of-the-ring.

4. **"No anchor in this class is ever computed inside the mid zone, so the pass-through can never fire for the zone" — SLIGHTLY OVERSTATED, but the conclusion survives.**
   Counter-case: a Blue-half best mine whose anchor is X-clamped to 0 *and* whose |Y| ≤ 840 IS inside the zone, so the literal-spec pass-through would fire for it. That makes the literal spec's zone-staging **incidental and mine-Y-dependent** (it works only when the chosen mine happens to sit near the centerline) rather than a capability. TASK-266 (e) re-verifies mid-staging as an acceptance check; staking that on mine-Y luck is not acceptable. Conclusion unchanged.

**Additional checks I ran on the deviation that the programmer did not claim:**
- **No half-law violation.** The zone straddles X = 0, so a zone-clamped anchor could in principle sit at X < 0. It cannot here: every anchor that can reach the zone branch is a rule-2 anchor already X-clamped to `BotHalfBoundaryX` (0), so `ZoneClamped.X ∈ [0, 800]`. And even if it were negative, TASK-262's gate already legalizes a Red-owned zone point by design (CONVENTIONS spawn-enable seam).
- **No player/bot asymmetry in the bot's favor.** The player may hand-place *anything* inside a Blue-owned zone (TASK-261); with the deviation the bot may auto-anchor only rule-2 economy plays there. The bot remains strictly *less* capable — the conservative direction.
- **Self-healing failure mode.** If the zone flips mid-match, `CanTeamSpawnHere` goes false on the very next call and the clamp silently reverts to the castle box. No latch, no stale state.
- **No new identifier**, signature matches the board's `FVector ClampAnchorToBotSpawnRegion(const FVector& Desired) const`, and the revert is genuinely ~10 lines + one header paragraph.

**Ruling.** Requiring the literal spec would knowingly ship a build that (a) makes the bot half of the capture-zone feature dead code, (b) fails its own next task's acceptance (e), and (c) contradicts Jonathan's directive ("when captured, you can spawn units there") for the bot only — in exchange for no safety the deviation doesn't already provide, since the deviation is provably inert whenever a Red-owned zone doesn't exist. **ACCEPT the deviation as the shipped behavior.**

**Action for the manager (documentation only, no code change):** reconcile TASKBOARD "W1-PREP appendix 3a" and CONVENTIONS line ~186 anchor-clamp law from "*else per-axis clamps ΔX/ΔY about `GetCastleRedLocation()`*" to "*else per-axis clamps into the NEARER eligible region — the castle box, or a Red-owned `CaptureZone_Center` — about that region's origin*".

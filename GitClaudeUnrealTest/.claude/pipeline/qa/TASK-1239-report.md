## The ruling on the staged-build question (asked by the orchestrator; the programmer asked for it too)

**Question.** Bullet 1 requires the pre-screen to run against `<stage>\Windows\<shim>.exe`. Every source describing the instrument says the verifier drives Play-In-Editor: doc §1 (`unreal_editor` = "Play-In-Editor control and verification (input simulation, screenshots, profiling)"; the only launch tool named is `launch_unreal_project`, which starts the EDITOR), doc §4 step 7 ("Aura verification can pre-screen"), plan item 8, and the verifier draft body ("a Play-In-Editor run through Aura's verification tools", "confirm the editor is up … before any PIE call"; no shell, no exe-launch tool). Nothing anywhere says Aura can drive a packaged binary. So as drafted the pre-screen's precondition is presently unsatisfiable. BLOCKER (rewrite as "PIE on the same commit, labelled NOT the shipped bytes") or WARN?

**Ruling: WARN. And the proposed BLOCKER remedy must NOT be adopted, because it would be a `SHIP-§9`-class defect for this particular gate.**

1. **What `C3` detects.** `C3-BOOT-ARENA` exists because of `PKG-§5a`: a cook that dropped soft-referenced content (cards, HUD, hero) while every gate stayed green. Its subject is the COOKED BYTES.
2. **What PIE renders.** PIE runs the editor's uncooked content graph. A PIE session on the same HEAD as a `PKG-§5a`-broken stage shows a full deck, a HUD and a hero — it answers "fine" in exactly the case the gate exists to catch. That is `SHIP-§9`'s stated class verbatim ("an instrument that answers correctly in the ordinary case and lies in precisely the case the gate exists to catch"), and `ship.md:142` already names the consequence: `PKG-§5a` "all over again with our own gate as the false witness". Labelling it "NOT the shipped bytes" makes the label honest and the evidence still worthless for `C3` — worse than absent, because it sits beside the capture as "ADDITIONAL evidence for Jonathan" and biases the eye it is supposed to inform.
3. **Therefore "SAME staged build" is the only form in which the pre-screen carries evidential weight for `C3`.** The programmer's sentence is the true one; the spec's "against the STAGED shim" was right for the same reason. `SHIP-§8d`'s same-build rule ("his eye is never spent on one stage and the zip made from another") is the sibling law.
4. **Why an unexercisable precondition is not `SHIP-§9` here.** `SHIP-§9` condemns instruments that fail OPEN (pass when they should stop). An optional evidence step whose precondition is unmet fails CLOSED: bullet 4 makes the skipped case the identity — the procedure reads exactly as today, `ship.ps1` is untouched, the human adjudication stands. No verdict, no gate, no path changes. The rule is not a gate that cannot be shown its failure; it is a capability condition on an optional add-on, and the row that answers whether the condition can ever be met is `TASK-1216-B` (the census) — a census fact the text must not pre-empt (`SC-§101`). Two honest futures: the census names an exe-launch + observe tool (the step becomes live as written), or it does not (the step stays dormant and should then be retired or rewritten by the manager, `SC-§100`).
5. **The residual hazard, and why it is a WARN rather than nothing.** The text forbids PIE without saying WHY, and does not say the step is presently unavailable. The plausible failure is not a false pass in `ship.ps1` (impossible by construction) but a mis-labelled provenance: an orchestrator wanting the pre-screen runs PIE and describes it as "against the stage" (`SC-§71b`, a claim the tool cannot have produced). One added sentence closes that — the fix in finding 1. Also stated as a lead, not a finding (`SC-§101`): even with an exe-launch tool, "quoted widget observations" from a Shipping exe would need Aura in-process; whether the Aura plugin has a runtime module that the cook now includes (it is enabled in `.uproject` since `0399d1c`) is unmeasured and is a `PKG-§` question for the next `/ship`'s `C4`-class sweep, not this text's.

**Remedy ownership.** The one-sentence sharpening is the programmer's (inside §2b.1a, still §2b-only). If the manager later rules the step must instead be retired pending the census, that is a rescope and a board edit (`SC-§100`), not a QA remedy.

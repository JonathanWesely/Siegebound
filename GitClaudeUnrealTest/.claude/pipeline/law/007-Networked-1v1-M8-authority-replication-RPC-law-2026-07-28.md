## Networked 1v1 (M8) — authority, replication + RPC law (2026-07-28)
Added 2026-07-28 (M8 kickoff, GDD §9.8; Jonathan: *"If it is ok to run it in parallel, go ahead and get started on M8"*). Binding on every M8 task and on ALL future gameplay code (single-player code written after this date must not add new violations).
- **AUTHORITY MODEL (manager ruling, flagged default):** LISTEN SERVER — the host is server + Blue player; the joining client is Red. **Strictly server-authoritative gameplay** per GDD §9.8: gold, spawns, combat, spells, upgrades, commands all mutate ONLY on the authority; clients request via RPC and render replicated state. Dedicated servers, OnlineSubsystem/EOS/Steam sessions, matchmaking and accounts are OUT OF SCOPE this milestone (GDD §10) — join flow = LAN/direct-IP (`open <ip>` / subsystem-wrapped travel).
- **RPC naming law (UE convention, now house law):** `Server<Verb><Noun>` (Reliable, `WithValidation` on every input-bearing server RPC), `Client<Verb><Noun>`, `Multicast<Verb><Noun>`. Every gameplay mutation a player initiates moves behind a `Server*` RPC on the OWNING controller (card play, placement confirm, spell target, discard, group-order confirm, upgrade purchase). Cosmetic-only effects may multicast; never gameplay state.
- **Replication law:** replicated properties registered in `GetLifetimeReplicatedProps` (`DOREPLIFETIME`/`_CONDITION`); client-side reactions in `OnRep_<Property>` handlers (exact naming; **RATIFIED at the TASK-353 sign-off: bool properties drop the `b` prefix in the handler name — `bDestroyed` → `OnRep_Destroyed`**); `HasAuthority()` guards at every mutation site (a mutation without a guard is a QA FAIL in M8 code); visual client-side systems (MIDs, decals, widget fills) DRIVE from OnReps, never from client-computed gameplay state. **Net log category: `LogSiegeNet`** (the `LogSiege<Domain>` law; declared/defined in `SiegeSessionSubsystem.{h,cpp}`, usable by any M8 code — both P1 lanes compile together at integration). **The P1 architecture is SIGNED (2026-07-28): `handoffs/TASK-353-architecture.md` D1–D14 — on any conflict between a board summary and the signed doc, the doc wins.**

- **⚖️ NET RELEVANCY LAW (added 2026-07-29 — the P1 two-client gate failure: match-critical state replicated under UE's DEFAULT 150 m relevancy inside a 500 m arena ⇒ scatter never replicated (client 0 gold nodes vs host 6) and the FAR castle's HP/crumble/destroyed never replicated (488 m: host 500 / client 2000; the near castle at 12 m was fine). The OnRep code was correct — relevancy was the defect. THREE TIERS, and EVERY replicated class DECLARES its tier:**
  - **TIER A — `bAlwaysRelevant = true`: match-critical singletons/near-singletons whose truth must not depend on where a camera is.** Fixed, tiny population (≤ ~10 actors), low-frequency event-driven state ⇒ bandwidth is negligible. P1 membership: GameState-class, PlayerState-class (**engine already sets these — VERIFY and document, do not blind-set**), **both `ACastle`s**, **`ASiegeBattlefieldScatter`**. A singleton that drives world generation or a win condition is ALWAYS Tier A.
  - **TIER B — ARENA-SCALED `NetCullDistanceSquared`, derived from ONE named constant, never a per-class literal.** For actors that are gameplay-relevant anywhere in the arena but numerous. The constant is `SiegeNet::ArenaRelevancyDistance` (one-concept header `SiegeNetLimits.h`, the `TeamId.h` precedent) = full arena diagonal × 1.1 — **currently 60,000 uu ⇒ `NetCullDistanceSquared` 3.6e9**; when the arena grows again (M7.6 may), ONE constant changes and every Tier-B class follows. **This is exactly why option (b) alone was rejected: a per-class literal is a drift trap that every future class must remember.** P1 membership: `AHeroCharacter` (a player's own pawn is owner-relevant regardless; the ENEMY hero must read across the arena).
  - **TIER C — engine default relevancy:** purely local/cosmetic actors (VFX, props) with no gameplay truth to carry.
  - **DECLARATION DUTY (the anti-drift half):** every new replicated class states its tier in a header comment AND in its task handoff; **"tier not declared" is a QA FAIL**, as is a Tier-B class carrying a hand-typed distance. **P2 WAVE DUTY: the unit fleet is Tier B by default and must be BANDWIDTH-MEASURED at full fleet** — a blanket `bAlwaysRelevant` across dozens of units is explicitly WRONG; if the measurement hurts, the lever is update-frequency throttling / `NetUpdateFrequency` and dormancy, NOT shrinking the arena band (units must be visible marching).
  - **D9 CORRECTION (recorded so the signed doc is not misread):** the scatter's "client obstacles are a SUPERSET of the server's ⇒ never rubber-bands" argument is VOID unless the seed actually arrives — under default relevancy the client got a strict SUBSET (zero), the exact inversion the design promised to avoid. **The argument's precondition is Tier A membership**; the doc's §3.5 reasoning is otherwise intact.
  - **COROLLARY — `HasAuthority()` and non-replicating actors (⚠️ AMENDED 2026-07-29: the manager's original APPLICATION of this was REFUTED by QA against installed UE 5.8 source, `qa/TASK-356.md` loop-1 — the correction travels with the law; the principle survives, the diagnosis does not).**
    - **THE NARROW PRINCIPLE (true, keep it):** an actor **spawned LOCALLY ON A CLIENT** with `bReplicates = false` keeps `ROLE_Authority`, so `HasAuthority()` returns TRUE there and any authority guard on it silently inverts. Never guard gameplay on `HasAuthority()` in a locally-client-spawned non-replicating class.
    - **THE APPLICATION THAT WAS WRONG (recorded so it is not re-derived):** I read the flagged fourth item (a client `ServerRequestPlayAgain` executing locally while its own PC read `bReplicates=False`) as proof of the inversion. It is not. **NET-SPAWNED actors — PlayerController, pawn, PlayerState — take their roles FROM THE CHANNEL**, so a CDO-level `bReplicates=false` on a client's own PC is NORMAL: `APlayerController`'s constructor never sets it (only `ANoPawnPlayerController`, PlayerController.cpp:6813); the SERVER enables it per-instance at login (World.cpp:4936-38) and the flag is not itself replicated. Moreover `AActor::GetFunctionCallspace` (Actor.cpp:5467-5666) **never reads `bReplicates`** — a client's only non-Remote outcome is Absorbed-with-`LogNet`-warning, which does NOT execute the body, so it cannot produce the observed "body ran, no warning, host silent". **Nothing in P1 was mis-guarded.**
    - **THE ACTUAL CAUSE — A TEST-LANE ARTIFACT, and this is the durable clause: NEVER VALIDATE RPC ROUTING FROM PYTHON REMOTE-EXEC.** `FEditorScriptExecutionGuard` (declared in `PyUtil::InvokeFunctionCall`, PyUtil.cpp:644) sets `GAllowActorScriptExecutionInEditor` (ScriptCore.cpp:455), which is the **FIRST branch** of `GetFunctionCallspace` (Actor.cpp:5469-74) ⇒ callspace **Local**. A python invoke therefore CANNOT distinguish a working relay from a broken one — it forces local execution either way. **RPC routing is verified ONLY through the real input path (the actual button / key / UI the player uses), never a scripted invoke.** Any verification claim about a `Server*` RPC sourced from remote-exec is void on its face.

- **🪤 RIG-ANCHOR OVERSHOOT — THE DIRECTION IS **UP**, AND THE PROJECT WROTE IT BACKWARDS IN FOUR PLACES (added 2026-08-01; MEASURED at TASK-372, independently re-derived by QA in `qa/TASK-372-tooling-report.md` §4).**
  - **The mechanism:** `rig_character.py` fits every SiegeBiped anchor as `z(frac) = base + frac × H`, where `H` is the **measured mesh bbox height** and the `*_z` fractions are documented as *"fractions of measured mesh HEIGHT (0 = feet, 1 = head-top)"*. An **overshooting prop — antlers, a tall staff, a crown, a banner — inflates `H`**, so for a fixed fraction the anchor lands **higher in absolute Z, i.e. HIGHER ON THE BODY.**
  - **⚠️ THE RIG SLIDES **UP**, NEVER DOWN.** The plan text, the TASK-369 gate rationale, `rig_character.py:216-218`'s comment and `rig_manifest.json`'s `_doc.proportions_override` all state it as *"anchors land too LOW / slides the whole rig down the body"* — **that is backwards.** A maintainer reasoning from the stated direction could "fix" a *correct* override and break a shipped rig. **Worked example, Sorcerer:** inflated bbox 181.805 vs true body 172.42 ⇒ inflation factor **1.0545**; uncorrected `neck_top` = 0.865 × 181.805 = 157.27 UE = **0.9121 of the true body** — the neck anchor rides **up into the skull**.
  - **⇒ THE CORRECTION RULE (unchanged by this entry — the *divide* was always right, only the prose was wrong): `corrected_z = nominal_z / inflation_factor`,** where `inflation_factor = measured_bbox_height / true_body_height`. Sorcerer: `neck_top_z` 0.865 / 1.0545 = **0.8203**. QA recomputed all 16 shipped Sorcerer overrides this way and matched to 5 dp.
  - **ONLY THE HEIGHT-SCALED KEYS ARE CORRECTED.** The 15 `*_z` keys **and** `foot_forward_frac` multiply `H` and are divided; the `*_x_frac` keys (`hip_x/foot_x/clav_x/sho_x/elb_x/wri_x`) multiply the **measured half-widths** `hh`/`sh`, never `H` — dividing them would have narrowed the rig by 5.45% for no measured reason. **The rule: divide what multiplies `H`; leave what multiplies `sh`/`hh`.**

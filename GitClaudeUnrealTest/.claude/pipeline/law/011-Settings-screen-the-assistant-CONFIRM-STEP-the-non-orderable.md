### 5. ⚖️ THE CONFIRM STEP + THE TOGGLE — AND THE ONE LAW THAT MAKES THE TOGGLE SAFE

**The confirm step is the `AwaitConfirm` state that Wave 1's B2 already owed** (§1: *"confirm-before-execute with ghost circles on the ground is a requirement, not polish"*). It is not new architecture; **what is new is that it is now user-visible and user-controllable.**

- **WHAT `AwaitConfirm` SHOWS:** (i) a **game-authored** one-line summary of the parsed order, filled from reason codes and the template table — ⛔ **never a model-produced string** (§3), and (ii) the **ghost circles on the ground** via the shipped `ASiegePlayerController::SpawnGroupCircleDecal`. **Accept executes; Cancel discards and returns to `Idle` with NOTHING partially executed.**
- **THE TOGGLE'S DEFAULT IS `true` — ON — AND THE DEFAULT IS ARGUED FROM THE MEASUREMENT, NOT FROM CAUTION.** §1's table shows **4 of 5 stable failures are wrong-place / wrong-count**, i.e. precisely the class a ground preview makes obvious in one glance. **A player who turns it off has chosen to trade that; a player who never saw it did not.**
- ⛔ **THE LAW THAT MATTERS MOST HERE — THE TOGGLE REMOVES A **HUMAN REVIEW STEP** AND NEVER A **MACHINE CHECK**.** With the toggle OFF, the FSM skips `AwaitConfirm` and executes. **It does NOT skip the parse, the `Kinds.Num() == Counts.Num()` invariant, the shortfall/clarification path, the eligibility checks, the authority refusal, or the §5-below non-orderable guard.** ⚠️ **A future task that "simplifies" the off-path by short-circuiting any of those is turning a UX preference into a safety regression, and it is an automatic QA FAIL.** The tell is simple: **every check that runs with the toggle ON runs with it OFF.**
- ⛔ **AND THE TOGGLE TOUCHES NOTHING OUTSIDE THE ASSISTANT.** §2 is unchanged and unchangeable: every keyboard command still works byte-identically, the console is never a requirement, and **no setting may ever gate a key.** A settings entry that can disable a keyboard command is out of scope by law.

### 6. ⛔ THE NON-ORDERABLE-KIND GUARD — MODEL-INDEPENDENT, AND EXPLICITLY **NOT** A ROUTE TO THE GATE

This is **shipped safety**, full stop. ⚠️ **Any handoff, QA report or board entry that lists this guard under an accuracy heading is factually wrong and is failed at the gate.**
- ✅ **IT IS UNIT-TESTABLE WITH NO MODEL RESIDENT, AND THAT IS THE REASON IT IS CHEAP.** The predicate reads the roster the snapshot already computes (`KindOrderable`, live today at `SiegeAssistantSnapshot.cpp:490/559/565/1131` and currently **private**). - ⚠️ **THE REFUSAL REUSES THE EXISTING UNSUPPORTED-ASK OUTCOME AND INVENTS NO NEW PLAYER-FACING SURFACE.** `{"ask":"unsupported"}` already exists in the grammar and already has a template. **The guard routes to it; it does not author a new one** (§3 — every player-facing string is a game-authored template).

### 19. ⚖️ THE SNAPSHOT-BUDGET CONSTANT FAMILY HAS **THREE** ROLES, NOT TWO — AND THE SAFE DIRECTION *AND* THE FAILURE MODE DIFFER IN EACH (2026-08-03)

**§10 named two roles (AUTHORITY and PRE-FILTER) and ruled that the safe direction INVERTS between them. A third role was in the code the whole time and had no name — and it is the one where getting it wrong is worst.**

| role | constant | safe direction | ⚠️ FAILURE MODE IF WRONG |
|---|---|---|---|
| **AUTHORITY** — stands between the snapshot and the budget | ~~`MaxSnapshotChars` 1085~~ **RETIRED** | assume the **SMALLEST** plausible chars/token ratio | over-admits ⇒ silent budget overrun |
| **PRE-FILTER** — a cheap gate before tokenizing | `SnapshotPreFilterMaxChars` **3000** | assume the **LARGEST** plausible ratio | too low ⇒ **silent truncation**; too high ⇒ one wasted tokenize |
| **TRIMMER** — decides how much ROSTER to PRINT (`BuildZoneC`) | **`SnapshotTrimBudgetChars` 1085** (**NEW NAME, value deliberately unmoved**) | **tight** | ⛔ **too high ⇒ THE PLUGIN BOUNDS REJECT THE TURN — the player's order is REFUSED, not degraded** |

- ⛔ **THIS IS WHY RE-POINTING THE RETIRED CONSTANT WOULD HAVE BEEN A REAL DEFECT AND NOT A TIDY-UP.** The retired `MaxSnapshotChars`' **only real code reader was the ROSTER TRIMMER** — neither the authority nor the pre-filter. **Both plugin bounds REJECT**, so aiming the trimmer at the pre-filter's `3000` would have converted ***"gracefully narrow the roster"*** into ***"refuse the player's order"*** — ⚠️ **a graceful degradation silently promoted into a hard failure, on a mid-battle interaction.**

  ⇒ ⛔ **THIS IS EXACTLY WHY *RE-POINTING* IS MORE DANGEROUS THAN *INTRODUCING A NEW NAME*: re-pointing carries the VALUE across and SILENTLY CHANGES THE ROLE**, and the value looking familiar is what makes it pass review. **`SnapshotTrimBudgetChars` shares `1085` with the retired authority value by coincidence of arithmetic, not by kinship** — and it holds that value **only because §12c freezes Zone B/C bytes this wave.** ⚠️ **When that freeze lifts, the trimmer is re-derived on its own terms and MUST NOT inherit whatever the authority becomes.**

### 18. ⚖️ "ADDITIVE" IS A CLAIM ABOUT **BEHAVIOUR**, NOT ABOUT DIFF ARITHMETIC — AND WHEN A RELAY CONTRADICTS THE BOARD, THE BOARD WINS (2026-08-03)

#### 18a. THE PROOF SHAPE DEPENDS ON THE TASK SHAPE, AND USING THE WRONG ONE FORCES A WRONG REFUSAL OR A SILENT VIOLATION

| task shape | what "provably additive" MEANS | the proof |
|---|---|---|
| **ADDS** code (a new binding, a new call, a new member) | nothing existing changed behaviour | ✅ **deletion count UNCHANGED** — insertions only |
| **EXTRACTS** a shared body (TASK-397 / 440 / 454) | ⛔ **deletions are REQUIRED and unavoidable** | ✅ **every deleted line ACCOUNTED FOR AT ITS NEW HOME, itemised line-by-line** |

- ⛔ **AN "UNCHANGED DELETION COUNT" DEMAND ON AN EXTRACTION IS UNSATISFIABLE ALONGSIDE A ONE-IMPLEMENTATION CONTRACT, AND THE CONTRADICTION IS FORMAL, NOT A MATTER OF DEGREE:** two handlers cannot **both** keep intact copies of a sequence **and** there be exactly one implementation of it. **Demanding both forces the implementer to either refuse a correct task or violate one constraint silently.**
- ⚠️ **THE GENERAL DEFECT: A METRIC THAT IS A VALID *PROXY* IN ONE TASK SHAPE BECOMES AN *IMPOSSIBLE CONSTRAINT* IN ANOTHER — and it keeps its authoritative tone the whole way across.** ⇒ **State the PROPERTY (*"no existing behaviour changed"*) and let the proof follow the shape. Never pin the proxy as if it were the property.** ⚖️ **Same family as §13's comparator and §14's search: the measurement's domain silently stopped matching the claim.**

> **The board and CONVENTIONS are the CONTRACT. A Slack post, an orchestrator relay or a dispatch-prompt paraphrase is a MESSAGE.** *(SLACK.md: "if Slack and the files disagree, the files win" — restated here because it just fired on a technical constraint rather than on status.)*

### 34. ⛔⭐ THE RE-DERIVATION LEDGER LAW — WHEN A **DEFINING DIMENSION** MOVES, EVERY CONSTANT DERIVED FROM THE OLD ONE IS ENUMERATED AT DECOMPOSITION, MARKED IN THE HANDOFF, AND RE-ENUMERATED AT THE GATE (2026-08-15)

> ### ⛔ **A TASK THAT CHANGES A *DEFINING DIMENSION* OF A SHIPPED ASSET OR ACTOR — ITS SCALE, BOUNDS, FOOTPRINT, OPENING, ANCHOR GEOMETRY OR COLLISION EXTENT — SHIPS A **RE-DERIVATION LEDGER**: ONE ROW PER CONSTANT THAT EXISTS *ONLY BECAUSE THE OLD VALUE WAS WHAT IT WAS*, EACH MARKED (i) RE-DERIVED, WITH THE ARITHMETIC, (ii) DELIBERATELY UNCHANGED, WITH THE REASON, OR (iii) OUTSIDE THIS TASK'S OWNERSHIP AND ⛔ NAMED TO THE TASK THAT OWNS IT.**
> ### ⛔ **AND THE SECOND LEG, WHICH IS WHAT MAKES IT ENFORCEABLE — THE GATE RE-RUNS THE ENUMERATION ITSELF AND PASTES ITS OWN LIST.** ⚖️ **A ledger that lives only in a handoff is a ledger nobody re-derives.**

- ⛔⛔ **WHY THIS IS A SEPARATE CLASS FROM `SC-§33`, AND WHY IT IS WORSE: THE COMPILER *AND* THE SUITE BOTH STAY GREEN, AND THE GAME IS SUBTLY WRONG.** A stale derived constant is a **legal number in the right type**. `SpawnBoxHalfExtent` left at the old castle's width still compiles, still passes every test, and simply stops containing the castle it was defined to contain — a defect that surfaces as *"units spawn inside a wall"* at a playtest, weeks later, attributed to spawning.
- ⭐ **THE PROJECT HAS ALREADY PAID FOR THIS ONCE, WHICH IS THE ONLY REASON IT IS A NUMBERED CLAUSE.** CASTLE-3X (2026-07-28, TASK-347..351) changed ONE dimension and had to hand-hunt: **`SpawnBoxHalfExtent`** (a THREE-way paired tunable — `ACastle` ≡ `ASiegePlayerController` ≡ `ASiegeBotController`) · **`DA_BattlefieldScatter`'s castle keep-clear radii** · **`CastlePlinthClearance` / `IsPointInsideCastlePlinth`** (retired outright) · **`GateBlockerExtent` + `GateBlockerRelativeLocation`** · the **HP-bar widget Z** · the **22-hull `UCX` set** · and the **`SM_Castle_Crumble01/02/03` trio**. ⚠️ **Not one of those is findable by grepping the changed value** — they are findable only by asking *"what did somebody compute FROM this?"*
- ⚖️ **THE ENUMERATION QUESTION, STATED SO IT IS REPEATABLE:** for each candidate, *"if the old dimension had always been the new one, would this constant have been written differently?"* **Yes ⇒ it belongs in the ledger, even if the answer turns out to be "leave it".** ⛔ **Silence is not a row.**
- ⛔ **THE HUMAN-SCALE EXEMPTION IS PART OF THE LEDGER, NOT AN ESCAPE FROM IT.** Some derived numbers are keyed to a **body**, not to the asset: step heights, doorway clear heights, capsule radii, interaction radii, camera offsets. ⚠️ **Those must be marked (ii) DELIBERATELY UNCHANGED and the reason named — because scaling them is the defect.** *A castle 3× taller does not get 3× the step height; the units did not grow.*
- ✅ **WHAT DISCHARGES IT: the ledger table, one row per constant, plus the gate's own re-enumeration.** ✅ **A ledger whose every row reads "already correct" is a RESULT and is reported as one** (`SC-§22`'s closing rule).
- 📌 **THE STRUCTURAL ESCAPE, PREFERRED WHERE AVAILABLE: DERIVE AT RUNTIME FROM THE ASSET INSTEAD OF TRANSCRIBING A NUMBER.** A half-extent read from `GetComponentBounds()` cannot go stale. ⚠️ **It is not always available or desirable (an `EditDefaultsOnly` tunable Jonathan can feel is worth a transcription) — but when a constant is a pure multiple of a measurable, the multiple is the honest thing to store.**

### 33. ⛔⭐ THE TRAILING-DEFAULT LAW — A NEW TRAILING DEFAULTED PARAMETER IS A CALL-SITE HAZARD **NO COMPILER AND NO TEST CAN SEE**. THE ADDING TASK PASTES A CALL-SITE GREP; THE GATE RE-RUNS IT (2026-08-05)

> ### ⛔ **A TASK THAT ADDS A TRAILING DEFAULTED PARAMETER TO AN EXISTING FUNCTION OWES, IN THE SAME HANDOFF, AN ENUMERATION OF *EVERY* EXISTING CALL SITE OF THAT FUNCTION — PRODUCED BY A GREP WHOSE EXACT COMMAND AND RAW HIT COUNT ARE PASTED — WITH EACH HIT CLASSIFIED AS (i) UPDATED, (ii) DELIBERATELY LEFT AT THE DEFAULT, WITH THE REASON, OR (iii) OUTSIDE THIS TASK'S OWNERSHIP AND ⛔ NAMED TO THE TASK THAT OWNS IT.**
> ### ⭐ **THE OBLIGATION HOLDS EVEN WHEN THE TASK MAY NOT EDIT THOSE FILES** — naming a call site costs two lines and is the entire control.
> ### ⛔ **AND THE SECOND LEG, WHICH IS WHAT MAKES IT ENFORCEABLE: THE QA GATE RE-RUNS THAT GREP ITSELF AND PASTES ITS OWN COUNT.** ⚖️ **A mechanism that lives only in a handoff is a mechanism nobody runs.**

- ⛔ ***"Every existing call site stays byte-identical"* IS THE *BENEFIT* OF THE SHAPE. IT IS NEVER THE AUDIT.** Both instances below shipped that sentence in place of a call-site list; it was **true both times and useless both times**.

**⛔⛔ TWO PROPERTIES MAKE THIS CLASS UNIQUELY DANGEROUS, AND THEY ARE WHY THE OBLIGATION IS MECHANICAL RATHER THAN ADVISORY:**

1. ⛔ **NO COMPILER DIAGNOSTIC AND NO TEST CAN CATCH IT.** The omission compiles **by definition** — that is what the default is for. And a test cannot reach it when the caller is private and world-driven: **TASK-549 stated plainly it CANNOT test the `Build` case** (`ComposeTurnGrammar` is `private` and world-driven) ⇒ ⛔ **the suite stays GREEN with the feature DEAD.** ⚖️ **A grep is the ONLY available mechanism**, which is why this law names a tool instead of an intention.
2. ⛔ **IT MISDIAGNOSES — THE FAILURE ARRIVES WEARING ANOTHER SUBSYSTEM'S CLOTHES, AND THAT IS THE EXPENSIVE HALF.** A dropped `RegionPlaceNames` yields a grammar with **no `inplace` rule at all**, so `{"in":…}` is **unsamplable at runtime while every one of nine tasks is individually correct**. ⚠️ **`AS-§21.11` outcome 5 primes the playtest to read *"the model never emitted `in`"* as the prompt UNDER-TEACHING a new shape** ⇒ **the batch would have been declared a MODEL failure when it was a WIRING failure** — and the next wave would have spent a few-shot, and an argument about a sealed corpus, on a missing function argument.

When the same struct grows a field twice, buy the overload.**

### 32. ⛔ A SAFETY MECHANISM THAT HAS NEVER BEEN **OBSERVED TO FUNCTION** IS NOT KNOWN TO FUNCTION (2026-08-03)

> ### ⛔ **AN ASSERTION THAT HAS ONLY EVER BEEN GREEN IS NOT YET PROVEN LOAD-BEARING.**
> **33 of 33 tests passed on their FIRST execution ⇒ not one has ever been observed to FAIL. Single run, no shuffle, flakiness unmeasured.** ✅ **That is a real and welcome result — and it is a different claim from *"these 33 assertions protect us."***

- ⚖️ **THE PROOF THAT CONVERTS *PRESENT* INTO *PROVEN* IS A DELIBERATE MUTATION: BREAK ONE THING, CONFIRM THE RIGHT TEST GOES RED.** ⚠️ **This wave already produced the worked example without meaning to — `ZoneA.NullVocabularyIsNotTheMeasuredLane` ASSERTED THE EXACT IDENTITY THAT BROKE THIS MORNING, and caught nothing, because it had never been run.** ⇒ ⛔ **A guardrail nobody has watched trip is a guardrail nobody has tested.** ✅ **Same family as §20 (trace before you type) and §22 (a citation is a lower bound): the artifact looks authoritative and its authority has never been exercised.**
- ⛔ **THE SECOND FORM, AND IT IS WORSE BECAUSE IT WEARS THE COSTUME OF CAUTION: A REDUNDANCY THAT SILENTLY DEGRADES TO A SINGLE POINT OF FAILURE IS WORSE THAN NO REDUNDANCY — BECAUSE IT IS *BELIEVED*.** TASK-470 passed the map **two ways** as belt-and-braces; ⚠️ **Git Bash MSYS mangled the positional `/Engine/Maps/Entry` into `C:/Program Files/Git/Engine/Maps/Entry`, which failed to resolve**, so **the `-ini:` override was the ONLY mechanism that worked** — and nothing said so. ⇒ ⛔ **Every limb of a redundancy is verified to work ON ITS OWN, or the redundancy is decoration.**

### 31. ⛔ A PRESENTATION LAYER MAY NOT **REPAIR** ITS INPUT (2026-08-03) — and on this feature it is the whole point

> ### ⛔ **A DISPLAY SHOWS WHAT IT WAS GIVEN. IT MAY NOT TIDY, SUPPRESS OR NORMALISE MALFORMED INPUT — BECAUSE THE STEP THAT EXISTS TO EXPOSE ERRORS CANNOT BE THE STEP THAT HIDES THEM.**

**THE INSTANCE (TASK-471, F1).** The parser permits `who:[…]` on **charge / fallback / rally**, so ***"Fall back 5 footman"* is REACHABLE.** ⛔ **No choice of frame can repair it — the verb is INTRANSITIVE, so the defect is the DATA COMBINATION, not the sentence.** **The fix sat inside 471's own function** (suppress the selection for non-selection-bearing verbs) — ✅ **and it REFUSED.**

- ⚖️ **THE REASONING IS THE FEATURE'S ENTIRE RATIONALE IN ONE LINE: JONATHAN APPROVED THE CONFIRM STEP *BECAUSE* THE MODEL GETS THINGS WRONG.** **4 of the 5 stable eval failures are wrong-place / wrong-count on orders the model otherwise understood** — the confirm step exists so he can SEE that before it executes. ⇒ ⛔ **A display that quietly tidies malformed output removes the only place he can see it, and it does so most effectively exactly when the model is most wrong.**
- ⛔ **AND IT WOULD HAVE BEEN INVISIBLE — WHICH IS WHAT MAKES IT DANGEROUS RATHER THAN MERELY WRONG.** A suppressed selection produces a **clean, grammatical, confident sentence.** The player sees a tidy order and approves it; the malformed command still executes. ⚖️ **Same shape as §20's `|| ShouldAbortNow()`: a plausible local fix that manufactures a confident-looking wrong result — except this one manufactures it on the review surface itself.**
- ✅ **THE CORRECT DISPOSITION, AND IT IS THE GENERAL RULE: PRESENT THE MALFORMED INPUT FAITHFULLY, AND ROUTE THE REAL DEFECT UPSTREAM.** ⛔ **A cosmetic patch at the display is not a fix; it is a decision to stop measuring.** ⚠️ **The upstream defect here is real and gets its own task — the grammar/parser admits a selection for intransitive verbs.**
- 📌 **THE NARROW EXCEPTION, SO THIS IS NOT MISREAD: a display MAY choose a frame that reads correctly across all LEGAL inputs (that is §30, and it is required). What it may not do is make an ILLEGAL input look legal.** ⚖️ **The tell: does the change alter which INPUTS are distinguishable on screen? If yes, it is repair, not presentation.**

### 30. ⛔ A TEMPLATE SUBSTITUTES **NOUNS AND NUMBERS** — NEVER **GRAMMAR** (2026-08-03)

> **Substitution points carry THINGS: a kind, a count, a place, a verb-as-a-whole-word. ⛔ They never carry PREPOSITIONS, articles, conjugations or agreement — because a grammar fragment is only meaningful in combination with the words around it, and a template cannot see those.**

- **THE INSTANCE: `DescribeCommandForPlayer`'s single frame `"{Intent} {Selection} to {Place}"` renders *"Guard 8 footman **TO** mine_near — accept?"*** ⛔ The preposition is wrong for **Guard** and **Ambush**, and it appears **on the confirm line AND the executed line of every such order** — i.e. **on the exact surface Jonathan asked for.**
- ⛔ **AND THE OBVIOUS FIX IS THE WRONG ONE: `{Preposition}` IS BARRED.** ⚖️ **A substituted preposition is a LOCALIZATION FRAGMENT, NOT A SENTENCE** — it is grammatically bound to both the verb before it and the noun after it, and those bindings differ per verb and per language. **A frame assembled from fragments produces sentences no reviewer can check and no translator can repair.** ⇒ ✅ **Use a VERB-NEUTRAL FRAME instead: one string that reads correctly for every intent.**
- ⚖️ **AND THE COUNT RULE FROM §22 STILL BINDS: ONE STRING, NOT THREE.** Forking the frame per intent trades a wrong sentence for **three sentences that will drift** — which is precisely what the shortfall row's own spec forbade one task earlier. **The same wave produced both instances: the verb (TASK-465) and the preposition (TASK-471).**
- ✅ **THE TEST: read the frame aloud with EVERY value its path can supply.** ⛔ **If any combination is ungrammatical, the frame is wrong — not the value.**
- ⚖️ **DEEPER THAN THE ABOVE, AND FOUND BY APPLYING IT (TASK-471): WHEN NO SUBSTITUTION CAN MAKE A RELATIONAL CLAIM TRUE ACROSS ALL ITS VALUES, THE FRAME MUST STOP ASSERTING THE RELATION.** `to` is a **DESTINATION** for send / charge / fall-back / rally and a **LOCATION** for guard / ambush — ⛔ **no English preposition is true of both.** ⇒ ✅ **The frames now PRESENT the place instead of RELATING it: `"{Intent} {Selection} ({Place})"` and `"{Intent} ({Place})"`.** ⚖️ **A frame that cannot state a true relation must state none — a false relation is worse than a terse one, because it reads as information.**
- ⛔ **AND A FRAME IS NESTED INSIDE WRAPPERS, SO ITS DELIMITERS MUST *COMPOSE* — THE THIRD §20 REFUSAL OF THE WAVE CAME FROM MISSING THIS.** A dash form was suggested and traced: `{Order}` is **never read alone** (`Assistant_ConfirmPrompt` = `"{Order} - accept?"`), so it renders **`Guard 8 footman - mine_near - accept?`** — **two dashes at one level, which no reader can group.** ✅ **Parentheses are SELF-DELIMITING and compose into all three wrappers.** ⇒ **Choose delimiters by how they nest, never by how they look in isolation.**

### 29. ⛔ A GATE COVERS THE TASKS IT **NAMES** — REVIEWING A *FILE* IS NOT GATING A *TASK*. EVERY BATCH CARRIES A COVERAGE LEDGER (2026-08-03)

> ### ⛔ **NO ARTIFACT LISTED WHICH TASKS THE GATES COVERED VERSUS WHICH TASKS EXISTED. Every gate named its own scope; NOTHING CROSS-CHECKED THE UNION AGAINST THE BATCH ROSTER — so TASK-442's code shipped in `cd5f4ed` with NO gate naming it, and it was found at FLIP time, not at GATE time.**

- ⛔ **THE RULING, AND IT GOES AGAINST THE CHEAP ANSWER DELIBERATELY: A RETROACTIVE SCOPED GATE IS OWED — *"it was probably covered"* IS THE EXACT UNEXAMINED-AUTHORITY PATTERN §15/§20 EXIST TO STOP.** ⚖️ **Consistency decides it: at TASK-461 and TASK-462 the rule was *code that changed after a PASS needs a verdict, no exception for "it only fixes the build."* A task whose review was NEVER SCOPED has a WEAKER claim than one whose review merely predated a diff — so it cannot receive a MORE generous ruling.** ✅ **The real mitigation SCOPES the remediation; it does not replace it: the gate covers only what no prior gate named, and it is small precisely because the file was genuinely read.**
- ⚠️ **AND THE BREACH IS RECORDED AS A BREACH.** The hard gate is *"nothing is committed to Git without a PASS QA report (code)"*, and by the letter **442's FSM skeleton was committed without one.** ⛔ **Do not write this up as "covered in substance."** The commit stands (reverting green, reviewed-in-file code would be worse), **the remediation is the retroactive gate, and the record says what happened.**

> ### ✅ **THE FIX IS ONE LINE PER TASK: EVERY BATCH CARRIES A COVERAGE LEDGER — `task → gate` — AND THE UNION IS CROSS-CHECKED AGAINST THE ROSTER *BEFORE* THE INTEGRATION COMMIT.**

- **The manager writes it at decomposition and updates it as gates land; build-master REFUSES TO COMMIT until every code task in the batch names a gate** (or names an explicit, reasoned exemption). ⚖️ **This is the cheapest possible control for the most expensive possible miss, and it would have caught 442 at gate 446 rather than at the flip.**
- ⚠️ **NOTE WHY IT WAS INVISIBLE: EVERY INDIVIDUAL GATE WAS CORRECT AND COMPLETE FOR ITS OWN SCOPE.** ⛔ **The defect existed only in the UNION, which no artifact expressed** — the same shape as the QUIET-MODULE LAW (*"each batch's own board looks safe in isolation"*). **A property of a set cannot be checked by inspecting its members one at a time.**

> ### ⛔ 29b. THE COMMIT-PATH LIST IS **DERIVED FROM THE COVERAGE LEDGER + THE GATE'S RATIFICATIONS** — ⛔ NEVER HAND-AUTHORED (2026-08-05)

**THE INSTANCE (batch AI-COMMANDER, `qa/TASK-550.md` WARN-4).** TASK-551's spec item (5) mandated commit **by explicit file path only** (GIT HAZARD LAW (d)) and its list **OMITTED `Source/GitClaudeUnrealTest/Siegebound/Tests/SiegeAssistantGrammarTest.cpp`** — a file TASK-549 edited under a **DECLARED** scope departure that the gate then **RATIFIED**. ⇒ ⛔ **As written, the batch's one commit would have left a ratified, gated edit UNCOMMITTED and the tree dirty afterwards.** ✅ **Build-master committed correctly — but because it reconciled its own `git status` against the list, ⛔ not because the list was right.**

- ⚖️ **THE STRUCTURAL FAULT, AND IT IS A TIMING FAULT: THE PATH LIST IS WRITTEN AT DECOMPOSITION; THE RATIFIED FILE SET IS ONLY FINAL AT THE GATE.** A hand-authored list is therefore a record of the manager's **expectations**, and ⛔ **every ratified scope departure is a way for a real file to fall OUT of the commit — silently, because a missing path raises no error, it just makes a smaller commit.** ⚠️ **`SC-§15` exists to make declared departures SAFE; this is the one way a departure can still cost something, and it costs it at the last step.**
- ✅ **THE RULE: the build task's path list is DERIVED — the coverage ledger's tasks, each task's `names:` block, PLUS every departure the gate RATIFIED, which the gate states AS PATHS.** ⇒ **A ratification is what adds a path. The manager's list is the starting point, ⛔ never the authority.**
- ⛔ **THE THIRD LEG, AND THE ONLY MECHANICAL ONE: BUILD-MASTER RECONCILES ITS OWN `git status --porcelain` AGAINST THE DERIVED LIST AND REFUSES TO COMMIT ON ANY DIFFERENCE IT CANNOT EXPLAIN** (`SC-§9` — a spec may say *"run the check"*; it may never say *"the list is complete"*). ⚖️ **The list and the working tree are two independent statements about one set; a difference is a finding about one of them, ⛔ never a rounding error.**
- 📌 **DUTY ON THE GATE: state ratified departures as PATHS, not as prose** (*"TASK-549's edit to the grammar test is ratified"* is a ruling; ⛔ it is not a commit instruction until it is written as a path).

### 27. ⚖️ A COMPILE-FIX DIFF IS **CODE** — IT NEEDS A VERDICT, AND THE GATE IS SCOPED TO **THE DIFF**, NOT TO THE TASK (2026-08-03)

> **Any code change made AFTER a PASS needs its own verdict before commit — the hard gate admits no exception for *"it only fixes the build."* ⛔ BUT THE GATE COVERS THE DIFF, NOT A RE-REVIEW OF THE ALREADY-PASSED TASK.**

### 25. ⛔ COMMIT-VERIFICATION IS **PER FILE KIND** — THE LFS TAG THAT PROVES A DOCS COMMIT CLEAN PROVES AN ASSET COMMIT BROKEN (2026-08-03)

**`handoffs/TASK-434-buildmaster.md` §1b established: *"every object tagged `(Git: …)`, not one `(LFS: …)`."* ⛔ THAT IS A **DOCS-ONLY** RULE AND IT INVERTS FOR ASSETS.** `.uasset` routes through the **`lfs` filter** ⇒ **`(LFS: …)` is CORRECT for an asset**, and ⛔ **a `.uasset` tagged `(Git: …)` IS THE DEFECT** — it means the binary went in raw, and **git history is append-only: a raw blob stays raw forever** (GIT HAZARD LAW (b)).

| commit contains | expected `git lfs status` tag | ⛔ the defect |
|---|---|---|
| `.md` · `.cpp` · `.h` · `.csv` · `.cs` · `.ini` | **`(Git: …)`** | any `(LFS: …)` |
| `.uasset` · `.umap` · `.dll` · `.lib` · `.png` | **`(LFS: …)`** | **any `(Git: …)`** |

- ⚖️ **SAME FAMILY AS §19 AND §23: a check whose correctness depends on a property of what it is checking, applied uniformly, silently inverts.** ⇒ **State the file kind, then the expected tag — never carry a tag expectation across commit kinds.**
- ✅ **VERIFY WITH `git check-attr filter -- <path>` PER KIND BEFORE COMMITTING**, and paste it (§7's *"acceptance, not assertion"*).

#### ⛔⛔⭐ 25b — **AN LFS-TRACKED PATH IS ⛔ NEVER VERIFIED BY *SIZE*. IT IS VERIFIED BY `oid` vs THE WORKTREE `sha256`** (added 2026-08-16; bought by TASK-570, which caught it *before* the `add` and therefore did not ship it)

> ### ⛔ **UNDER LFS THE INDEX HOLDS A ***POINTER***, NOT THE CONTENT. EVERY SIZE-SHAPED INSTRUMENT AIMED AT IT MEASURES THE POINTER — AND THE ONE REFINEMENT THAT LOOKS LIKE THE FIX ***PASSES THE FAIL WORLD***.**

- ⚠️ **THE MEASURED CASE, IN BOTH ITS FORMS.** A commit spec directed: *"run `git cat-file -s :Content/UI/WBP_WarMap.uasset`; `33193` ⇒ correct, `23105` ⇒ the empty shell is still staged."*
  - ⛔ **RAW FORM — STRUCTURALLY BLIND: `git cat-file -s` returned `130` BEFORE the `git add` and `130` AFTER it.** It is the pointer's length. **It can never return either expected number**, and the spec's own "≈130 ⇒ STOP" rule then fires on a perfectly correct commit. ⇒ **The instrument is unsatisfiable in the pass world and uninformative in the fail world — `(f)`'s general shape exactly.**
  - ⛔⛔ **REFINED FORM — WORSE, BECAUSE IT *CERTIFIES* THE WRONG BLOB: reading the pointer's own `size` field returned `33193` — THE EXPECTED NUMBER — ON THE STALE BLOB.** The index did not hold the predicted 23,105-byte empty shell; it held a **DIFFERENT 33,193-byte version** (the first of two compile-saves, auto-staged by the editor's SCC between them). ⇒ ⚖️ **A size check would have matched, passed, and written a stale widget into an append-only history.**
- ⛔ **THE ONLY INSTRUMENT THAT SEPARATES THE TWO WORLDS — because the oid *is* the content digest:**
  ```
  git cat-file -p :<repo-relative-path>     → oid sha256:<X>   size <N>
  sha256 of the WORKTREE file                → <Y>
  X == Y  ⇒ the index holds what is on disk.   X != Y ⇒ STALE — re-`add` and re-read.
  ```

RE-`add` ***EVERY*** `AM` PATH AND VERIFY EACH BY DIGEST.** ⚠️ **The spec named ONE path; THREE carried it.** `SM_Torch` was staged at **81,557 B** against a worktree **86,796 B**, and `SM_WarTable` at **83,463 B** against **93,688 B** — ⛔ **neither was flagged anywhere, by anyone.** ✅ **The discharge is a full sweep: all 17 committed binaries verified oid-vs-sha256 after staging AND again against the commit — 17/17.**

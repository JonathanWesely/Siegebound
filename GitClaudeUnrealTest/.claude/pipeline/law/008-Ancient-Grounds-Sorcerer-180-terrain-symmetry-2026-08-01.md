### 1. THE 180°-ROTATIONAL SYMMETRY LAW (supersedes the asymmetric-scatter law at "Battlefield & procedural terrain (M6.5)" and the X-mirror wording in the mines law)
- **The transform, exactly — the ONLY legal terrain symmetry on this project:** for every placed instance/actor, the twin is
  `loc' = (−X, −Y, Z)` · `yaw' = Fmod(yaw + 180, 360)` · `scale' = scale (UNCHANGED)`.
  This is a proper rigid motion on the yaw-only/uniform-scale transforms the scatter uses: **no negative scale, no HISM winding flip, no approximation.** The retired X-mirror was a fake reflection and is dead.
- **Generation method (Jonathan's, and it is the better algorithm): generate ONE HALF, then duplicate rotated 180°.** Half the RNG draws, half the ground traces, the same ~15,000 `AddInstance` calls, the same perf budget. Per-layer `TargetCount` semantics already count primary + twin, so a target of 340 becomes ~170 pairs.
- **⚠️ GENERATE THE BLUE HALF (X ≤ 0). THIS IS NOT ARBITRARY AND MUST NOT BE FLIPPED:** `PlayerStart` exists ONLY at **(−23800, 0, 100)** — there is no Red-side PlayerStart (`SiegeGameMode.cpp:684-687` confirms the fallback IS the design). Generating Blue means the PlayerStart keep-clear disc (r=800) is honored for real and its rotated image over-clears a harmless empty patch at (+23800, 0). Generating **Red** would let a legally-placed prop rotate **onto the hero spawn** — broken. The mine pass already draws `X < 0`, so this is consistent, not new.
- **ZERO RNG DRAWS IN THE ROTATION STEP (hard QA criterion).** The twin is computed, never sampled. This is what preserves intra-build determinism and host==client. Same binary + same seed ⇒ byte-identical layout and byte-identical log lines.
- **Existing seeds WILL produce new layouts. That is EXPECTED and is NOT a regression** — documented precedent: the TASK-140 draw-order change did exactly this ("Radius-aware scatter placement" law, M6.6). The contract that must hold is *intra-build* reproducibility + host==client, never cross-build layout stability.
- **Inline, never a bulk post-pass.** The twin is emitted inside the per-instance loop, because three shipped invariants die under a post-pass: `VisualToProxy` index parallelism (tree visual + collision proxy must be added in lockstep or the cull paths orphan visible trees), `SpacingGrid` registration of the twin, and `HillSurfaceComponents` registration for pass-1 blockers.
- **Twin ground Z is RE-TRACED (`GroundZAt(−X, −Y)`), never copied** — it preserves the null-safe code shape, and under an exact rotation it MUST return the primary's Z, which converts an assumption into a free QA assertion.
- **The hill-parity rollback machinery becomes DEAD CODE and is DELETED.** `TryResolveMinePair`'s clone/re-trace/rollback path exists because the fake mirror could land a twin off the cloned hill's footprint; under a true rotation the twin lands on the geometrically identical point of the rotated hill — same Z, same slope, always. Deleting it is part of the law, not an optional cleanup.
- **Config:** the `bool bMirrorSymmetric` toggle on `USiegeScatterConfig` is REPLACED by an explicit single global symmetry-mode field. The `GenerateScatter seed=… mirror=…` log token stays **grep-able** (QA reads it) — it records the new mode value.
- **Deliberately still asymmetric, and that is correct:** `ValidateTraversability`'s destructive culls (`CullCorridorBlockers`, `RemoveBlockingInstancesInDisc`) stay side-agnostic (mirroring a cull would delete more geometry for zero traversability gain) — but they **LOG when they fire**, because they locally break symmetry; the PlayerStart keep-clear disc (one real + one harmless rotated over-clear); and near-origin self-pairing (a grass blade at (−10,10) rotates to (10,−10) — cosmetically invisible, and blocking layers are already excluded near Y=0 by the corridor rule).
- **🚩 KNOWN RESIDUAL, OUT OF SCOPE, NEEDS A FRESH JONATHAN RULING:** both castles read **yaw 0** (three independent in-engine readbacks) and `ACastle` puts its gate blocker on the local −Y side, so **both castle gates face world −Y** — the one gameplay-visible asymmetry left under this law. Fixing it means `Castle_Red` yaw 180, which is an `L_Arena` SAVE, and the one-time exception is **SPENT** (`bf5e562`, "the never-save law resumes in full"). Flagged, not done. *(Already fine: the 8 POI landmarks and the two gold-node props at (0, ±5000) are already exact 180° rotational pairs; ground/boundaries/navmesh bounds/capture zone are centered and therefore rotation-symmetric.)*
  **⚖️ CLOSED 2026-08-27 — the fresh Jonathan ruling ARRIVED (CASTLE ROTATION, `ROT-§0`; TASK-662..668):** he ordered BOTH castles rotated so the gates face the battlefield center (Blue yaw +90 → gate +X, Red yaw −90 → gate −X — the ROT-§1 expected values, measured before saved) with a NEW explicit, ordered `L_Arena` save exception, spent at TASK-662. ### 4. The permanent stacking damage boost (mechanic rules — UPROPERTY defaults, NEVER CSV columns)
- **Storage is `int32 PermanentDamageStacks`, NEVER a float.** The UI's whole job is distinguishing **exactly** 100/200/300% from just-past-them; a float accumulated over 80 additions of 0.05 makes "exactly 100%" epsilon-dependent. Integer stacks make the band boundaries exact by construction. Mirrors `AHeroCharacter::SharpenedBladeStacks`.
- **On `ASummonedUnit`:** `int32 PermanentDamageStacks = 0` (VisibleInstanceOnly, Transient) · `float PermanentDamageBonusPerStack = 0.05f` (`// GDD §x.x`, EditAnywhere) · `int32 MaxPermanentDamageStacks = 80` (`// GDD §x.x` — 80 × 5% = the **+400% cap**) · `float GetPermanentDamageMultiplier() const` (**BlueprintPure**, the QA readback hook) `= 1.f + PermanentDamageBonusPerStack * PermanentDamageStacks`.
- **Compose point — ONE line in `ComputeOutputDamage`, immediately after the War Banner aura:** `Output *= GetPermanentDamageMultiplier();` — multiplicative, exactly 1.0 at zero stacks. One insertion covers **both melee and ranged** and every keyword unit. **NEVER mutate `AttackDamage` in place** (house buff law).
- **ALSO compose onto the Sapper blast** — `ApplyDetonation` currently passes raw `AttackDamage`, bypassing the chokepoint: `const float BlastDamage = AttackDamage * GetPermanentDamageMultiplier();`. **This is a deliberate change to a shipped unit** (dying IS how a Sapper attacks; an unboosted blast would be a visible lie). Charge/Slayer/Aura are deliberately NOT retro-applied there — that is a separate pre-existing gap, recorded, not fixed here.
- **Mutation + eligibility API (pinned):** `void AddPermanentDamageStacks(int32 Stacks)` (clamps to Max; **broadcasts ONLY on an actual change**) · `void ClearPermanentDamageStacks()` (reset path: **UNCONDITIONAL broadcast**) · `bool CanReceiveDamageBoost() const` = `!bDead && CanEverAttack() && AttackDamage > 0 && Profile != Support`. That predicate excludes the Sorcerer, Miner and Cleric — units whose damage routes through neither compose point — which also keeps their boost row hidden. Authority is by construction (the sole caller is the gated ancient-ground tick): **comment it, do not bolt on a guard that buys nothing in P1.**
- **Reset:** `ClearPermanentDamageStacks()` in `HandleDeath`, next to the existing HP broadcast — required because the rigged-death path defers `Destroy()` up to 2 s, during which a boosted corpse would show a full boost bar. **Play Again needs ZERO work** (its step 2 destroys every unit). **Match-end freeze deliberately does NOT reset** — a permanent boost survives to the end screen; stated here so QA does not file it as a miss.
- **M8 P2 DUTY (record in the header, never silently omit):** `PermanentDamageStacks` becomes `UPROPERTY(ReplicatedUsing = OnRep_PermanentDamageStacks)` when the unit fleet replicates, with the OnRep re-broadcasting so the client's seed-then-bind path is identical.

### 5. The boost bar — `WBP_CombatantHealthBar` is EXTENDED, never duplicated

No fixed `BarHeightZ` works, per-frame correction violates the never-per-tick law, and it would double the exact screen-space registration surface TASK-130 spent five attempts on. **The TASK-131 corruption fear does NOT apply here:** that was a Blueprint **class reparent** that orphaned BIE overrides; re-nesting `Bar` under a `VerticalBox` is a slot/outer change — the widget keeps its identity, name, variable binding and brush properties, and the parent class is never touched.
- **Widget-tree names are LAW (the artist and the C++ both read this block):**
  ```
  [ROOT] VerticalBox "BarStack"
    ├─ [0] Border      "BoostOutline"   slot Size=Fill 1.0, Padding 1.5 uniform, Pad Bottom 1
    │        └─ ProgressBar "BoostBar"
    └─ [1] ProgressBar "Bar"            slot Size=Fill 2.0   ← EXISTING, properties UNTOUCHED
  ```
  `DrawSize` in `CombatantHealthBarComponent.cpp` goes **(90, 12) → (90, 22)** — ~~boost bar ~5 px inside a 1.5 px frame (~8 px total) and health bar ~12 px, i.e. today's health-bar height exactly.~~
  ⛔⛔ **THE PIXEL SPLIT ABOVE IS ⛔ STALE — ⛔ STRUCK 2026-09-02, ⛔ MEASURED BY `TASK-861`.** ⛔ **The real split is ⛔ `7.00 / 1 / 14.00`, ⛔ not "~8 + ~12".** ⛔ **It ⛔ predates `TASK-368`'s `Fill 1.0 → 2.0` fix, which ⛔ changed the ratio and ⛔ nobody updated this line.** ⭐ **The ⛔ diagram above is ⛔ correct (it already reads `Fill 2.0`); ⛔ only the ⛔ prose was left behind — ⛔ which is exactly `SC-§38` cl. 4: ⛔ a law that ⛔ describes behaviour ⛔ rots silently while the ⛔ structural half stays true.**
  ⚠️⚠️ **AND THE ⛔ CONSEQUENCE THAT NEARLY SHIPPED: ⛔ `Bar` and `BoostOutline` are ⛔ `Fill` slots — ⛔ they absorb ⛔ every spare pixel.** ⇒ ⛔ **any ⛔ CONSTRUCTOR-TIME `DrawSize` bump resizes ⛔ EVERY health bar in the game** (⛔ measured: a `(90,30)` bump renders `Bar` at ⛔ 19.33 px ⛔ instead of 14.00, ⛔ on every building, the hero and all 20+ units). ⇒ ⛔ **a `DrawSize` growth for a ⛔ conditional segment must happen ⛔ AT THE EVENT, ⛔ never in the constructor or `BeginPlay`** (`TASK-860(4a)`). 📌 **Rider: the component ⛔ never sets `Pivot`, so the default `(0.5, 0.5)` grows the box ⛔ DOWNWARD into the actor's head — ⛔ decide it, ⛔ do not inherit it.**
- **The outline replaces the earlier colored-dot design (Jonathan's ruling).** A `UBorder` wrapping the progress bar paints its brush in the uniform padding ring = a clean frame. `UBorder::SetBrushColor(FLinearColor)` is a stock BlueprintCallable node, unlike a ProgressBar's `OutlineSettings` (no runtime BP setter; it would need a full `FProgressBarStyle` struct param — banned in a BIE). **Why it does the dot's job:** the ambiguity is "full bar of the lower color" vs "nearly-empty bar of the higher color", and the outline is visible at ANY fill level — 100% reads as a solid light-blue block, 100.1% as a grey bar in a **dark blue frame**.
- **Both new widgets use `WhiteSquareTexture`, `DrawAs = Image`, tint white.** A *material* fill brush swallowing a runtime tint was TASK-131's actual root cause — **do not reopen that door.**
- **`BoostBar` carries its OWN medium-grey track `(0.22, 0.22, 0.24, 0.85)`**; `Bar` keeps its near-black `(0.03,0.03,0.03)@0.7` track. This exists to solve the band-4 legibility problem (pure black on the near-black health track is ~1.3:1 — the strongest unit would get the worst indicator).
- **Hide via `SetRenderOpacity(0.0)`, NEVER `SetVisibility`** — a float pin (no enum, per the widget-param law), and it keeps the health bar pinned at a constant head offset for every unit, boosted or not. Set it on **both** `BoostOutline` and `BoostBar` (render opacity propagates to children — belt-and-braces).
- **C++ ↔ widget contract = ONE atomic BlueprintImplementableEvent** on `UCombatantHealthBarWidget`:
  `void SetDamageBoost(float FillFraction, float R, float G, float B, float RowOpacity);`
  ONE event, not two, because unlike the team tint **the color changes with the value** — splitting fill and color creates a frame where band-3 purple paints at a band-4 fill. **All banding math is C++; the widget is a dumb pipe with ZERO conditionals.** EventGraph = one linear exec chain, one `MakeLinearColor(R,G,B,1.0)` fanned to both consumers: `SetPercent(BoostBar, FillFraction)` → `SetFillColorAndOpacity(BoostBar, $C)` → `SetBrushColor(BoostOutline, $C)` → `SetRenderOpacity(BoostOutline, RowOpacity)` → `SetRenderOpacity(BoostBar, RowOpacity)`. **The alpha literal MUST be 1.0 — read it back.**
- **⚠️ `SetDamageBoost` landing as a `K2Node_CustomEvent` never fires from C++, silently — this exact defect hid the health-bar bug five times.** Author via `add_event`, assert the node's object **class** via `get_node_infos`, and **never trust `bIsImplemented`**.
- **Banding (in `UCombatantHealthBarComponent`, C++ only):** `Band = Clamp(CeilToInt(BoostPercent / 100), 1, 4)` · `Frac = Max((BoostPercent − (Band−1)*100) / 100, MinBoostFillFraction /*0.04*/)`. `CeilToInt` is upper-inclusive by design: **100% = full light blue · 100.1% = nearly-empty dark blue · 400% = full black**, with no special case.
- **Band colors — `EditDefaultsOnly FLinearColor` on the component (tint is DATA, never hardcoded in the WBP):**

  | Band | Boost | Linear RGB | ≈ hex | Contrast vs the boost track |
  |---|---|---|---|---|
  | 1 | 0–100% | `(0.55, 0.80, 1.00)` | `#C4E7FF` | 2.99:1 |
  | 2 | 100–200% | `(0.010, 0.020, 0.350)` | `#1927A0` | 2.96:1 |
  | 3 | 200–300% | `(0.200, 0.010, 0.420)` | `#7C19AD` | 2.09:1 |
  | 4 | 300–400% | `(0.010, 0.010, 0.014)` | `#191920` | **4.50:1 — the best on the bar** |

  The ramp darkens monotonically (light → navy → purple → black) so "deeper = stronger" reads without a tooltip. Band 3 is deliberately a DEEP purple — a bright violet computes to ~1.06:1 and vanishes. **Residual weak case, documented escalation:** the band-4 near-black *outline* sits against the world, not the track, so over a tree shadow it can disappear (the fill still carries the magnitude at 4.5:1). If the PIE gate flags it, the levers are: thicken the Border padding to 2.5 px, or set `BoostOutline`'s brush to `DrawAs=RoundedBox` with a 1 px light halo. **Do NOT ship a blind change — that ordering is the whole lesson of TASK-131.**
- **Data plumbing — `IHealthBarProvider` gains DEFAULTED virtuals (so `ABuilding` and `AHeroCharacter` need ZERO changes):**
  `DECLARE_DYNAMIC_MULTICAST_DELEGATE_OneParam(FOnCombatantDamageBoostChanged, float, BoostPercent);` · `virtual float GetDamageBoostPercent() const { return 0.f; }` · `virtual FOnCombatantDamageBoostChanged* GetDamageBoostChangedDelegate() { return nullptr; }` (**a POINTER, so "not boostable" is expressible**). In `BeginPlay`: **seed UNCONDITIONALLY** (this drives a non-boostable actor's row to opacity 0 rather than leaving the design-time state — the `qa/TASK-005` seed-then-bind law), **then** bind only if the delegate is non-null. `ASummonedUnit` must broadcast on **EVERY** mutation — the same discipline as `OnHPChanged`'s four sites; miss one and the bar is stale forever.

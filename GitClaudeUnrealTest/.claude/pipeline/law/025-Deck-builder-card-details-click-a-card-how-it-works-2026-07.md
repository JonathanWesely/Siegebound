## Deck-builder card details — click-a-card "how it works" (2026-07-23)
Added 2026-07-23 (TASK-268..272; Jonathan directive verbatim: *"lets change the deck builder interface a bit. Make it to where when you click on the display for a card it displays a detailed description on how the card works."*). EXTENDS the M6 deck-builder section above — it does not replace any of it. **Every M6 rule survives untouched:** per-card `MaxCopies` enforcement, the live x/50 counter (`TotalText`), the §8 average-cost guide (`AvgText`), deck-legal-only-at-exactly-50 (`PlayBtn` gate), save/load/active-deck, and the TASK-125 physical-card tile face. **⚖️ CARD-UNCAP rider (2026-08-28, `UNCAP-§`):** the per-card `MaxCopies` enforcement named in this section (and every "cap-grey"/"greys-at-cap" mention in this and the M6 section above) is SUPERSEDED — the deck cap is abolished; `GetCardMaxCopies` becomes a compat shim returning `SiegeLegalDeckSize` so the WBP cap-grey wiring survives without a .uasset edit (`UNCAP-§4`). Everything else in these sections still binds.

- **ADD/REMOVE DOES NOT MOVE (manager ruling).** The tile's existing `AddBtn` "+" / `RemoveBtn` "−" (TASK-118, kept in TASK-125's bottom caption plate) stay EXACTLY where they are, still calling `UDeckBuilderWidget::AddCopy` / `RemoveCopy`, still cap-greying via `SetIsEnabled(AddBtn, GetCountOf < GetCardMaxCopies)`. There is NO whole-tile click handler today (the card art is `SelfHitTestInvisible` precisely so it never eats +/− clicks), so "click the display" is a NEW, previously-unbound gesture — not a conflict. Details-on-click is therefore purely ADDITIVE.
- **The new click target:** `Btn_CardFace` on `/Game/UI/WBP_DeckCardTile` — a transparent, style-less Button covering the card FACE (art region), inserted as the **FIRST/bottom-most child of the tile's root Overlay** so the count plate and the caption plate (which carry `+`/`−`) sit ON TOP and win hit-testing. Handler `OnCardFacePressed` → `OwnerBuilder->SelectCardForDetails(CardID)` (IsValid-guarded, the `OnAddPressed`/`OnRemovePressed` shape). It must never call `AddCopy`/`RemoveCopy`.
- **Selection model lives in C++** (the M6 "C++ base owns ALL model/logic" law). On `UDeckBuilderWidget`:
  - `UFUNCTION(BlueprintCallable) void SelectCardForDetails(FName CardID)` — stores `SelectedDetailCardID`, fires `OnCardDetailsRequested(CardID.ToString())`. An unknown/None CardID clears the selection instead (and still fires, with an empty string).
  - `UFUNCTION(BlueprintCallable) void ClearCardDetails()` — clears + fires with an empty string.
  - `UFUNCTION(BlueprintPure) FName GetSelectedDetailCardID() const`.
  - `UFUNCTION(BlueprintImplementableEvent) void OnCardDetailsRequested(const FString& CardID)` — BIE params stay float/int/bool/byte/FString ONLY (the widget rule). The WBP re-reads the getters; it never receives a struct.
  - Private `UPROPERTY(Transient) FName SelectedDetailCardID`.
- **The description is GENERATED FROM DT_Cards, never authored per card (binding ruling — anti-drift).** `UFUNCTION(BlueprintPure) FString GetCardDescription(FName CardID) const` composes a multi-line player-facing string from the row's structured fields. **NO `Description` CSV column is added, and the existing `Notes` column is NEVER surfaced to the player** — `Notes` stays "designer notes; not used by gameplay code" (it carries GDD/implementation refs like "(GDD 3.0)" / "UPROPERTY on ADeepMine" and is already PROVABLY STALE: the `Lightning` row says "in 400" while its `AoERadius` is 700). A balance pass is pending in the Standing backlog; generated text auto-survives it, authored prose would not.
  - **Composition order (omit any line whose source field is 0/None/not applicable):** (1) identity line `"<Type> · Cost <Cost> gold"` with Type prose Unit/Building/Economy/Spell/Hero Upgrade/Utility — **⚖️ AMENDED 2026-08-28 (CARD-UNCAP, `UNCAP-§5`): the `· Max <MaxCopies> per deck` clause is DELETED; with the cap abolished it would state a rule the game does not implement — exactly this section's truth-law FAIL class. The hero-upgrade RULES-tail stack-cap line ("up to %d stacks", fed by `MaxCopies`) is UNCHANGED — still true, still data-driven**; (2) blank; (3) STAT block from `HP`/`Damage`(+`AoERadius` splash)/`Cadence`/`Range`(+melee vs homing-projectile per `bRanged`)/`MinRange`/`Speed`; (4) blank; (5) RULES block — one plain-English line per applicable clause, drawn from the glossary below.
  - **Glossary clauses** (each interpolates the row's OWN numbers wherever the number exists in the row): `bCharge`, `bSlayer`, `bSuicide`, `SwarmCount`, `ChainTargets`/`ChainFalloff`, spawner (`SpawnCardID`/`SpawnInterval`/`Lifetime` — resolve the spawned card's `DisplayName`, never print a raw CardID), `SpellEffect` (all five values), spell delivery (resolve `Auto` through the EXISTING `USpellLibrary::GetEffectiveDelivery` — never re-implement the per-effect default), `Profile` (Siege / Support prose; Standard omitted), and castle-damage scaling.
  - **Glossary-mirror rule:** magnitudes that are NOT CSV columns because they are mechanic rules living as UPROPERTY defaults (Charge 2 s / 2×, Slayer 150 HP / 2×, castle scaling 50 % projectile & spell / 200 % Siege, Deep Mine +2 gold/s, Masons 300 HP over 10 s, hero-upgrade magnitudes, Rally) appear as **named string constants in ONE place in `DeckBuilderWidget.cpp`**, each with a `// mirrors <Class>::<Property>` comment. Changing that gameplay value obliges updating the constant. Anything in a CSV column is read from the row and NEVER hardcoded (§3.0).
  - **Truth law (QA gate):** every rules line must correspond to behavior the SHIPPING code actually implements — the author verifies each clause against the owning class before writing it. If a clause cannot be verified, OMIT it. A description that states a rule the game does not implement is a FAIL, not a nit. No GDD section refs, no class/property names, no CSV column names in player-facing text. Target ≤ ~12 lines per card.
  - Unknown/None CardID ⇒ empty string (the WBP shows its own static hint); missing table ⇒ empty string, logged once (reuse the existing `bWarnedMissingTable` / `WarnedMissingRowIDs` spam guards). Never a crash.
- **The details view = a NON-MODAL SIDE PANEL inside `/Game/UI/WBP_DeckBuilder`** (manager ruling: not a modal, not an expanded tile — the player must be able to click card after card and keep using `+`/`−` while reading). **NO new WidgetBlueprint asset is created**: the panel is built in `WBP_DeckBuilder`'s existing runtime-constructed tree (TASK-118 technique). ⚠ **A new WidgetBlueprint may NEVER be produced by duplicate+REPARENT** — that has silently broken RUNTIME repaint in this project (design-time looked fine; ~9 wasted fixes). Build fresh or build inline.
  - Element names, EXACT: `DetailsPanel` (the panel's root container), `DetailsArtBorder` (card art, driven by the existing `GetCardArtTexture`), `DetailsNameText` (`GetCardDisplayName`), `DetailsCostText` (`GetCardCost`), `DetailsBodyText` (`GetCardDescription` — the multi-line body, `AutoWrapText` ON), `DetailsHintText` (static empty-state hint, shown when no card is selected), `Btn_DetailsClose` (clears the selection via `ClearCardDetails`).
  - The grid keeps its full card inventory: since the panel takes horizontal space, the 28-tile `WrapBox` is wrapped in a ScrollBox named `GridScroll` (closes the TASK-118 flag #3 overflow risk). Nothing else in `WBP_DeckBuilder` is disturbed — `TotalText`/`AvgText`/`SavedNamesText`/`NameInput`/`PlayBtn`/Back/Save/Load/Reset bindings stay byte-identical.
  - Legibility is law, not decoration (the M5.5 white-fill-on-white-track defect class): the body text sits on an opaque/dark backing plate, never directly on card art.

## Overhead unit health bars (M5.5) — RETIRED 2026-07-10 (superseded by "Overhead combatant health bars — REBUILT" above; kept for history)
Added 2026-07-09 (TASK-110..112; Jonathan directive: "add a health bar to every tower and character"). Broadens GDD §7 ("Enemy hero/units show floating health bars when damaged") to **every combat actor, both teams** — see the TASKBOARD "M5.5 manager decisions" rulings block for the binding scope/behavior calls. This is a SEPARATE system from the castle bar: castles keep `WBP_CastleHealthBar` + the `FOnCastleHPChanged` delegate (M1, TASK-018/019) UNCHANGED; the M5.5 system covers units, buildings, and the hero, which carry NO HP-changed delegate (ASummonedUnit::ApplyHealing comment: "Units carry no HP-changed delegate (only ACastle does)"), so the bar POLLS the HP getters instead of binding.
- **Shared read interface:** `IHealthBarTarget` (`UHealthBarTarget` UINTERFACE, `NotBlueprintable`), header-only `Source/GitClaudeUnrealTest/Siegebound/HealthBarTarget.h` (the `TeamId.h` one-concept-header precedent). Three pure-virtual const methods (the `ITeamAgent::GetTeamId` C++-interface shape, NOT BlueprintNativeEvent): `float GetHealthCurrent() const`, `float GetHealthMax() const`, `bool IsHealthBarActorAlive() const`. Implemented by `ASummonedUnit` (→ `GetCurrentHP`/`GetMaxHP`/`!IsUnitDead`), `ABuilding` (→ `GetCurrentHP`/`GetMaxHP`/`!IsBuildingDestroyed`), and `AHeroCharacter` (→ `GetCurrentHP`/`GetMaxHP`/`!IsDead`). Team is read through the EXISTING `ITeamAgent::GetTeamId` — never duplicated onto this interface. `ACastle` does NOT implement it (it keeps its delegate bar). `AGoldNode` does NOT implement it (not damageable — no bar).
- **WidgetComponent subclass:** `UHealthBarComponent` (a `UWidgetComponent` subclass), files `HealthBarComponent.h/.cpp` in `Source/GitClaudeUnrealTest/Siegebound/`. Exactly ONE instance is added in-constructor to each of the three base classes above, named `HPBarWidget` (reuses the `<Purpose>Widget` component-name convention and mirrors `ACastle::HPBarWidget`); subclasses (AMinerUnit, ATower, ABarracks, ADeepMine) inherit it automatically. The component owns: the soft widget class, the poll timer, the show/hide (hide-at-full) logic, and the one-time team-tint push. EditDefaultsOnly tunables (so BPs can tune with no code): `TSoftClassPtr<UUserWidget> HealthBarWidgetClass` (default `/Game/UI/WBP_UnitHealthBar`, null-safe — missing asset = silent no bar, never a crash), `float PollInterval` (default 0.15), `bool bShowHealthBar` (default true — per-actor/per-BP opt-out for anything a playtest flags as clutter, e.g. miners), `float BarHeightZ` (relative Z above the actor; default 120 units — buildings/hero BPs may raise it), `FLinearColor BlueBarColor` / `RedBarColor` (default to the §6 palette / `MI_TeamColor` linear values — Blue (0.05,0.30,1.00), Red (1.00,0.10,0.05); tint is data, never hardcoded in logic). WidgetComponent space = **Screen** (the `ACastle::HPBarWidget` precedent). DrawSize small (units read at ~150 px per the card-art bar) — pin ~90×12.
- **Widget C++ base + UMG asset:** `UUnitHealthBarWidget` (`UUserWidget` subclass), files `UnitHealthBarWidget.h/.cpp`; the UMG asset `WBP_UnitHealthBar` in Content/UI/ (`/Game/UI/WBP_UnitHealthBar`) is reparented to it (the `U<Name>Widget` ↔ `WBP_<Name>` law above). Two BlueprintImplementableEvents, **float params only** (MCP cannot author enum/struct BP params — CONVENTIONS widget rule): `OnHPChanged(float CurrentHP, float MaxHP)` — WBP implements it as ProgressBar `SetPercent(CurrentHP / MaxHP)` guarding `MaxHP > 0` (identical contract to `UCastleHealthBarWidget::OnHPChanged`, so `WBP_CastleHealthBar` is the fastest donor to duplicate); and `SetTeamColor(float R, float G, float B)` — WBP tints the FILL brush from the pushed RGB. The component drives BOTH: it seeds `SetTeamColor` once at init from the owner's team, and calls `OnHPChanged` each poll while the bar is shown.
- **Behavior law (ALWAYS-VISIBLE while alive, team-tinted fill) — REVERSED 2026-07-09 by Jonathan (playtest override of the shipped hide-at-full law from commit 9a8a75f):** the bar is VISIBLE the ENTIRE time the actor is alive (and opted-in via `bShowHealthBar`), at FULL HP included, and the FILL reflects `CurrentHP / MaxHP` live — it DROPS as the actor takes damage, exactly as a health bar is expected to behave (Jonathan verbatim: *"I want the health bar to be visible the entire time … see it drop as the character takes damage … it should drop, as you typically expect with a health bar"*). It is HIDDEN only on death/destruction (the component polls `IsHealthBarActorAlive`) and when `bShowHealthBar` is false. This SUPERSEDES the original M5.5 rule (bar shown only while `CurrentHP < MaxHP − epsilon`); the `HealthBarFullEpsilon` full-HP term is RETIRED from the show/hide decision (the show-gate becomes `bShowHealthBar && bAlive`). Team tints the FILL (blue friendly / red enemy per §6), fixed regardless of HP — the bar communicates team by color and damage by length; it never recolors green→red. Applies to BOTH teams. Donor unchanged: `/Game/UI/WBP_CastleHealthBar`; never author the tree from scratch (template-donor rule). Implemented by TASK-122 (component) + TASK-123 (WBP render).
  - **Bar colors (ITEM B, added 2026-07-10, Jonathan loop-1 playtest request: *"make the part of the bar that shows the health red if they are enemies and blue if they are friendly, and the background of the bar grey"*):** the FILL is team-tinted DATA (unchanged law): `UHealthBarComponent::BlueBarColor` (0.05, 0.30, 1.00) friendly / `RedBarColor` (1.00, 0.10, 0.05) enemy, pushed once via `SetTeamColor` → the WBP's `SetFillColorAndOpacity(Bar, …)` — never hardcoded in WBP logic. The fill's `fillImage.tintColor` MUST be neutral white (1,1,1 = identity multiply) so the pushed team color shows through undimmed. The BACKGROUND / unfilled TRACK brush is a FIXED neutral GREY authored ON `WBP_UnitHealthBar` — a STATIC widget style (like the bar's DrawSize / HitTestInvisible / no-baked-text), NOT per-actor data: it never varies by team or actor, so it is deliberately NOT a runtime-pushed C++ param (a background-color param would over-engineer a constant). **Manager ruling (delegated call): the grey lives as an authored WBP brush, RECORDED here as the canonical value** — dark neutral grey ~ linear (0.03, 0.03, 0.03) at ~0.7 alpha, which MUST contrast clearly with BOTH the blue and the red fill. This closes the round-1 contrast miss: TASK-123's WBP audit found the authored `Bar` `FillColorAndOpacity` AND `fillImage.tintColor` both set to WHITE, so a draining fill was near-invisible on a white/near-white track (the likely REAL round-1 bug — the C++ may only have been harmless hardening; see TASK-122 ITEM-A QA mandate). Implemented by TASK-127.
  - **OPEN QUESTION (flagged for Jonathan 2026-07-09, NOT silently decided) — does the `bShowHealthBar` opt-out survive?** The per-BP `bShowHealthBar` EditDefaultsOnly opt-out (default `true` — suppresses clutter on a flagged type, e.g. miners) is KEPT under the reversed law. Rationale: it is ORTHOGONAL to hide-at-full — it gates WHETHER a type carries a bar at all, not WHEN a bar shows — and always-on bars make a per-type opt-out MORE valuable, not less (60+ always-visible bars > 60+ damage-only bars in on-screen clutter, §6). Manager recommendation: KEEP, default `true`. If Jonathan wants literally EVERY actor's bar always-on with no exceptions, TASK-122 can drop the opt-out — his call; the recommended path ships either way (non-blocking).
